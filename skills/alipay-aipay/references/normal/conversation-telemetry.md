# 全 Skill 的会话授权与 Token Pay 摘要

脱敏消息先在本地入队，再通过原有 syncLog 通道异步上传。以下命令都经 `references/normal/scripts/runtime.mjs` 执行。采集偏好按本机当前系统用户保存，后续触发、切换 Agent 或普通 Skill 更新直接沿用；会话消息仍以宿主当前对话为边界，不合并不同聊天。它独立于[业务阶段与 RUN_ID](telemetry.md)。状态中的 `LOCAL` 表示本地采集可用，不表示上传关闭；上传开关及目录见[阶段记录说明](telemetry.md)。

共享配置文件为 `~/.alipay-aipay/telemetry-profile.json`，位于 Skill 安装目录之外，由脚本维护。同一系统账户的安装副本共用它，共用系统账户的人也共用偏好。文件保存 `user_id`、采集选择、声明版本、授权 ID 及防重复处理所需的消息／会话标识哈希。首次使用时，沿用现有机器标识和哈希算法生成 `user_id` 并保存，后续各 Agent 的会话采集、阶段上报及重试补传复用该值，每个进程首次读取后在模块变量中缓存。用户更新采集选择时保留该值。原 `conversation-preference.json` 中的有效选择与授权 ID 自动迁入新文件，成功保存后删除旧文件。`schema_ver` 是文件格式版本，`notice_version` 是采集声明范围版本，均独立于 Skill 版本。旧版每会话的 `.consent` 文件不迁移为长期授权，采集范围变化导致声明版本变化时需重新同意，已有拒绝继续生效。隔离演练设置 `ALIPAY_AIPAY_TELEMETRY_DIR`（兼容旧变量 `ALIPAY_AIPAY_NEW_TELEMETRY_DIR`）时，共享配置也存放在该目录下。

## 采集哪些消息

对已获授权且符合采集范围的用户消息和助手回复，能拿到完整正文时，逐字上报，保留标点、换行和格式，只把敏感片段替换为 `[REDACTED]`。拿不到完整正文时，可上报脱敏摘要，开头标注 `【摘要】`。无法确认主要内容时跳过该条。

当前授权有效且会话为 `ACTIVE` 时，以对话轮次为单位采集。

- 用户实际输入（query）逐条采集，包括问题、补充、选择、确认、纠正、操作结果和临时切换话题的用户消息。停止采集要求先按下方撤回流程处理。
- 助手每轮采集结束本轮时的完整正式答复，包括等待用户补充、选择、确认的回复，以及本轮结果交付，保留其中所有段落、列表和表格。执行中的进度播报、工具输出和内部思考不采集，宿主是否折叠这些内容不影响判断。
- 依据回复是否结束本轮、等待用户或交付本轮结果判断。最终答复中的方案、指引和校验结果一并保留。同轮中途独立展示后继续执行的消息按 flow 展示。用户询问进度或方案时，采集回答该问题的完整最终答复。`--final true` 是调用方对采集范围的确认。

例如，用户补充技术栈后，同一轮继续展示开发方案、沙箱摘要和校验结果，最后交付网站并说明开通状态：只采集技术栈输入及最后一条完整回复，中间展示的消息不采集。若中途确需用户补材料而结束本轮，则采集该阻塞回复，待用户回答后进入下一轮。

query/response 是 Agent 的取材范围，不新增 CLI 参数或上报字段。脚本不读取宿主消息通道，仍由 Agent 在传入正文前完成上述判断。业务阶段遥测另按原规则记录，不将阶段事件转换为会话正文。

## 授权与逐条记录

1. 每次触发用 `telemetry resolve-session` 取得 SESSION_ID，本轮所有命令都追加 `--session-id SESSION_ID`，包括恢复、撤回及子流程。CI 作业号或工程 ID 不能代表宿主会话。先运行 `conversation status`。用户本轮确认同意，或 preference 中已有有效的同意记录，均立即开始采集。已有记录时无需再次询问，从当前聊天触发 Skill 的那条用户消息开始记录。已有 `GRANTED` 时立即执行第 3 条的记录命令并检查成功回执，只查询状态不算采集。同一聊天的后续消息沿用同一个采集会话。已有 `DENIED` 直接沿用。仅 `LOCAL + UNSET` 时运行 `conversation notice`，按[主入口](../../SKILL.md#每次触发)原样回复完整声明，等待选择。`DISABLED` 时跳过正文记录。
2. 用户单独回复选择时，用 `conversation consent --reply <本轮采集选择> --input-id MESSAGE_ID`。同时表达采集选择和业务需求时，用宿主的结构化标准输入把完整回复交给 `conversation consent --reply-stdin --input-id MESSAGE_ID`，仅解析选择，原文不落盘。明确拒绝后同一轮继续处理业务，例如“不同意，直接帮我接入网页支付”。没有安全 stdin 时，明确拒绝可仅传固定选项“仅使用服务”；有条件、引用他人或相互矛盾的回复不可裁剪为同意。首次同意或拒绝后重新同意须对应本会话已展示的当前版本声明；沿用已有同意无需再确认。未明确时澄清；状态读取/写入失败时继续业务，不记录正文或摘要。选择“仅使用服务”或拒绝后为 `DENIED` 并持久保存：仍然按实际步骤记录阶段，**不调用任何会话消息／问题摘要记录命令，不生成、保存或发送 query、助手答复或摘要**。同一机器的其他系统账户及其他机器不继承这份偏好。
3. 状态为 `GRANTED` 时，首次实际调用 `telemetry start-conversation --message-id MESSAGE_ID --message-stdin`，从标准输入接收经语义脱敏的用户消息 JSON，取得 `CONVERSATION_ID` 和 `CONVERSATION_MESSAGE_RECORDED`。已有本聊天会话时复用，第 4 条命令继续记录。首次同意后，从当前上下文按原顺序补采本次知情说明覆盖的触发问题、采集说明、期间符合范围的问答与补充，以及用户的同意选择。后续触发沿用同意时，从当次触发问题开始采集。正文和摘要按上方规则取材，拒绝期间的消息不补录。拒绝或撤回后如用户主动要求加入，重新展示声明，获得新的明确授权，从新授权点开始。更换产品沿用当前采集会话。会话消息示意为 `{"role":"user","content":"月费会员续费通知如何验签？"}`，JSON 的 `content` 字段保存脱敏后的正文。使用宿主支持的结构化 stdin 写入，不拼接用户输入到 shell、命令行或临时文件。无安全 stdin 通道则跳过该条。
4. 采集有效期间，按原对话顺序逐条记录符合范围的消息。每条用户发言先判断是否要求停止采集，如有先按第 6 条撤回。其他用户消息通过 `telemetry conversation-message --conversation-id ID --message-id MESSAGE_ID --message-stdin` 记录，已有业务计数窗口时先执行原有 `count-user-input`。助手在本轮完整正式答复定稿后、发送前，用同一命令传 `--final true`、角色 `assistant`，提交随后发送正文的脱敏版本，正文不可得时按上方摘要规则处理。写入失败时重试当前消息，以成功回执为准。脚本先重试本地写入，仍无 `CONVERSATION_MESSAGE_RECORDED` 时，按错误标记修正输入或恢复存储，再用同一会话、同一消息 ID 和同一内容重试当前记录。已记录消息的重试返回原序号，回复回执丢失也按此处理。采集故障时正常交付，继续处理当前记录的重试，不能把读状态或下条消息成功当作本条成功。首次授权后按第 3 条补采，其余不回填后来发现的历史漏采，当前消息的失败重试继续执行。仅在已授权且会话为 `ACTIVE` 时提交，不采附件正文、凭据、临时链接、私有代码或无法安全脱敏的正文。内容相同但来自不同轮次的消息使用各自的 ID。业务 start-run 只接收任务与产品，转执行时无需再次提交触发问题。
5. Token Pay 六个明确能力，以 `--product-type` 传[阶段表中的产品类型](telemetry.md)。**仅对已授权且可安全概括的实际用户问题**，在同一条用户事件附上可选 `question_summary`：“周期订阅／自动续购／单笔支付／企业支付／数电发票／企业认证：用户询问（或希望、需要等）……”；要写清要解决的具体业务问题。每条消息至多一份，不为问候、确认或助手答复造摘要，不单独再发一次，不运行旧订阅采集器，不额外识别 IP 或模型。摘要格式、范围或脱敏校验不通过就丢弃该字段。产品未知可不传；只知大类可传 `token-pay`，此时不附摘要。
6. 用户撤回时，先执行 `telemetry opt-out --input-id MESSAGE_ID`；已知时可附 `--conversation-id ID`，将本机偏好更新为 `DENIED`；旧记录 ID 有误不影响停止选择。保存成功以 `CONVERSATION_CONSENT=DENIED` 为准。**从这条消息起**即停止会话消息和摘要（包括撤回这条本身），其他聊天的后续采集和待上传记录也按最新偏好校验，后续触发继续沿用拒绝，不影响阶段与业务。撤回使旧授权和旧 CONVERSATION_ID 失效；已记录的本地历史不表示获准继续投递。实际完成/用户结束当前任务时，若仍处于有效授权和采集状态，先按第 4 条记录最后的正式答复，再用 `telemetry end-conversation --conversation-id ID` 结束采集，随后实际发送该答复；任务结束不清除或改变保存的偏好。任一采集动作失败也正常交付。中途遇到阻塞或未回复不是任务结束，不伪造最终结果。

## 正文输入

Agent 语义脱敏和脚本补充脱敏统一使用 `[REDACTED]` 替换敏感内容；正文与可选 `question_summary` 均使用这一占位符，保留字段名和非敏感上下文，不附加类型或编号。

`start-conversation` 和 `conversation-message` 的 `--message-stdin` 必须实际收到一份 JSON。宿主支持直接传入结构化 stdin 时使用该方式；只有 `exec_command` / `write_stdin` 时按以下两步执行，不把正文拼进命令：

1. 用 `exec_command` 启动对应 runtime 命令，设置 `tty: true`、`yield_time_ms: 1000`，携带同一个 `--session-id` 和稳定的 `--message-id`。等待 `ALIPAY_AIPAY_INTERNAL:CONVERSATION_INPUT_READY=true` 并保存工具返回的进程 `session_id`；它与宿主 `SESSION_ID` 是不同的标识。没有就绪标记时先读取进程输出，不发送正文。
2. 脚本就绪后，用 `write_stdin` 向该进程写入 `chars: JSON.stringify(message) + "\n"`。正文包含的换行由 JSON 序列化转义，整份 JSON 以一个实际换行结束。脚本在等待期间关闭终端正文回显，60 秒未收到完整输入或取消时返回输入失败，不占用消息序号，按上方规则重试当前消息。

只有返回 `CONVERSATION_MESSAGE_RECORDED=<sequence>` 才表示本地记录成功，首次还应取得 `CONVERSATION_ID`。仅启动命令、进程退出码为 0 或 `CONVERSATION_INPUT_READY` 都不代表已记录或已上传。失败时检查 `CONVERSATION_INPUT_ERROR` 或 `CONVERSATION_RECORD_ERROR` 并重试当前消息。正文 JSON 和解析错误原文保留在内部处理。
