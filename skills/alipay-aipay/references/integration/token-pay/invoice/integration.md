# 数电发票接入

交付时按实际工程改动和验证结果说明接入进展，并注明验证是在本地模拟环境还是产品允许的非生产环境。

## 能力与资料

发票能力用于商家根据业务订单申请数电普通发票或数电专用发票，支持单笔/合并开票、红冲、查询、文件下载与状态通知。它可以与周期订阅、单笔收款及银行转账等业务配合，但付款、退款与开票是不同的业务动作。

官方资料入口：[数电发票文档](https://opendocs.alipay.com/pre-open/0k3k6p?pathHash=6b81e5a4)。接口参数见 [api-contract.md](api-contract.md)，重试、红冲、通知与验收见 [lifecycle.md](lifecycle.md)。

维护口径：2026-11-03 产品维护者确认发票能力已在线上运行。本组资料按当前接口实现整理；本次未取得上述网页正文，未重新执行真实开票，不把“正文暂不可读”解释为产品未上线。遇到资料未覆盖的权限、地区、费率、字段长度或平台协议，以商户当前正式文档、控制台和实际回执核对，不猜测，也不因此阻塞已经明确的工程工作。

## 开通与身份

- 发票产品需要商户实际开通；支付产品已开通不代表发票权限自动具备。
- 核对商户应用、发票产品权限、销方税号与开票服务授权。销方税号必须与签约主体一致；不在对话中索要私钥、服务授权密钥或登录密码。
- 优先沿用工程已有的支付宝 SDK、签名验签和凭据管理。发票业务参数放入 `biz_content`，应用身份使用网关公共参数，不在业务 JSON 中自造 `merchant_pid` 或内部身份字段。
- 用户明确使用服务商代调用时，核对发票产品正式支持的授权方式及通知接收应用；不要从接口前缀推导可用的 `app_auth_token` 合同，也不套用 B2B 的“仅自有应用”限制。
- 发票相关的页面登录、身份验证由商家在正式入口完成。不要编造开通 API、登录地址或二维码。

## 工程实施

先检查工程已有订单、支付记录、开票页面、通知入口和文件下载入口。按用户指定范围补齐：

1. 建立商家开票申请记录，保存商户请求号、关联业务订单、支付记录、票面快照及平台发票申请单号。订阅业务需要定位到实际收费订单；不能只拿 `subscription_id` 代替业务订单号或支付单号。
2. 从真实订单及商家确认的票面资料组装申请。税收分类编码、税率、购方抬头和销方信息使用商家实际配置，不根据“软件服务”等名称猜测税务属性。
3. 调用申请接口，持久化响应；提交中展示处理中。接口调用成功、申请已受理、开票成功、文件可下载分别记录。
4. 接收发票 OpenMQ 通知，并提供主动查询补偿；终态更新和业务处理应可重复执行而不重复产生副作用。
5. 成功后按需要获取 PDF/OFD/XML 下载地址，将 `expire_time` 作为有效期依据；展示下载失败与文件尚未准备好的可恢复状态。
6. 涉及红冲时增加原蓝票关联和红冲状态，保留原申请及票面历史，不覆盖成一张新的“已退款发票”。

商家按已获准的发票环境和授权订单办理，真实开票、红冲产生相应票据状态。默认先完成一笔蓝票申请 → 查询成功 → 下载文件 → 通知落地。用户要求合并或红冲时继续对应流程；不要求先完成所有可选能力才能接入。已授权的工程实现、产品允许的非生产联调和本地模拟可继续；本 Skill 不在生产提交开票、红冲、下载真实发票或触发业务通知。可核对商家提供的脱敏结果，不能据沙箱或样例认定真实开票。

## 与订阅及其他支付配合

| 场景 | 实施要点 |
| --- | --- |
| 每期续费后开票 | 接收付款结果，定位本期业务订单，再按商家规则发起独立开票申请；不能声称订阅平台默认自动开票 |
| 多笔订单合开一张 | 使用合并模式，保存完整订单集合及金额；后续重试和红冲保持原集合 |
| 退款或服务终止 | 分别追踪资金退款和发票红冲；一个成功不代表另一个成功，不臆定两者固定先后顺序 |
| 银行转账或其他支付 | 支付类型按实际记录填写，仍走发票契约；不因出现银行转账而切换到 B2B 创单流程 |
| 测试环境 | 沿用商家实际已获准的发票环境；订阅测试客户、沙箱 CLI 和测试时钟不构成发票沙箱可用证据 |
