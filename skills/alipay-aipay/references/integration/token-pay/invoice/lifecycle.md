# 发票生命周期、通知与验收

字段与方法见 [api-contract.md](api-contract.md)，实施顺序见 [integration.md](integration.md)。

## 请求号、额度与恢复

- `out_request_no` 是商户维度的申请幂等号。超时、连接中断或结果不明时先按原请求号查询，不通过换号重复开票。同号重试使用完整原请求，不能修改票面或订单金额。
- 普通申请结果 `SUBMIT` 表示尚未终态，继续查询或等待通知；`SUCCESS` 表示开票成功；`FAILED` 结合失败原因处理。若申请返回明确未受理或需要登录的失败，不能只凭申请返回状态推定此请求永久不可重试；按提示完成登录后，用同一请求号和完整原请求继续，并查询核对。不要虚构第三种 `invoice_mode` 作为“登录重试模式”。
- 已受理但结果未知时，不把网络错误视为明确失败，不立即释放商家本地额度或自动换号。终态失败与明确未受理的重试要区分，无法确定时保留原记录并查单。
- 同一订单集合受累计开票金额限制，处理中金额也影响可用额度；只有成功红冲才释放相应额度，提交红冲不等于已释放。
- 同一业务订单集合再次申请时，业务订单金额和支付快照应保持一致。订单尚在处理中或未全额红冲时，不能把它搬进另一个集合绕过额度限制。
- 不把“同号请求防重复”理解成“换个请求号就可以重复开票”。不要承诺平台自动替商家核实所有外部支付事实；请求来自商家的真实业务记录。

## 红冲

红冲通过 `alipay.trade.saas.invoice.apply` 提交新申请，使用新的红冲请求号、`invoice_main_info.invoice_type="2"` 和 `red_related_invoice_info`。原蓝票必须成功且属于当前商家。保留原蓝票申请号，红票的 `origin_invoice_no` 指向它，不填正式票号 `invoice_no`。

红票票种、开票模式、完整业务订单集合、各业务订单金额及支付明细沿用原蓝票；不能只保留发生退款的那条支付记录。商品行通过 `original_blue_item_serial_no` 关联原蓝票商品行，商品名称、编码、税率、单位、规格、优惠属性保持一致。不要为红票随意换商品或换税率。

| `red_reason` | 原因 | 关键约束 |
| --- | --- | --- |
| `01` | 开票有误 | 必须全额红冲，覆盖原全部商品行；金额、税额、单价和数量与原蓝票一致 |
| `02` | 销货退回 | 保持商品身份和单价；按本次冲减量及金额填写，受可红冲余额和渠道限制 |
| `03` | 服务中止 | 保持商品身份和单价；按实际冲减范围填写，受可红冲余额和渠道限制 |
| `04` | 销售折让 | 商品行 `price` 和 `quantity` 留空；按冲减金额填写，受可红冲余额和渠道限制 |

单笔且支付记录全部为支付宝支付的联用场景，仅允许全额红冲。合并开票及其他支付场景可涉及不同服务渠道，不能据此承诺任意部分红冲都可成功，仍需核对原因、明细、余额与实际渠道能力。不能把所有渠道都说成“只能全额红冲”。

红冲不会自动执行资金退款。退款成功不证明红冲成功；服务取消也不证明已退款或已红冲。订阅续费自动开票、退款自动红冲属于商家业务编排，只有明确实施并验证后才能作为已完成能力报告。

## 发票通知

消息标识为 `alipay.trade.saas.invoice.changed`，业务主体为 `invoice_detail_info`，字段结构与单笔查询详情一致，状态是 `SUBMIT/SUCCESS/FAILED`。不要使用订阅变更的 `change_type`，也不要套用 B2B 交易消息的主体字段。

使用商家实际配置的 OpenMQ 接收方式和官方 SDK/平台协议完成验证及应答。接收包的外层封装、签名位置和成功应答不能仅从业务主体推导；优先检查现有通知工程和平台文档，不凭空添加固定 HTTP 回调格式。不同应用代调用时确认实际接收应用，不保证通知总是发到商家应用。

处理流程：验证来源与应用身份 → 解析发票详情 → 按平台发票申请单号关联本地记录 → 幂等更新状态和票面结果 → 成功持久化后按协议应答。重复通知不能触发再次开票；迟到的提交中通知不能覆盖已确认终态；终态冲突或缺少信息时主动查询。未收到通知不等于开票失败，提供查单补偿并分别记录“平台成功”和“商家已收到通知”。

## 常见问题

以下为业务问题分类，不将内部异常名称当作已确认的网关 `sub_code`；错误码及外层返回以正式接口和实际回执为准。

| 现象 | 下一步 |
| --- | --- |
| 未开通或销方信息不匹配 | 核对发票产品权限、签约主体及销方税号，不能仅检查支付权限 |
| 同号请求冲突 | 对比完整原请求快照；恢复原参数，变更业务意图则先处理原申请结果 |
| 金额错误或余额不足 | 检查元/分转换、商品金额合计、业务订单去重、处理中及已开票/红冲金额 |
| 合并订单集合被占用 | 查询原集合申请及红冲状态；不拆换集合绕过约束 |
| 要求重新登录 | 商家在正式入口完成登录，保持原请求号和原完整参数重试 |
| 红冲不允许 | 检查原蓝票成功状态、原申请单号、原因、原商品关联、金额及渠道限制 |
| 成功但文件未就绪 | 保留成功状态，稍后重试下载；不能为获取文件再开一张票 |
| 下载地址过期 | 重新获取下载地址，以最新 `expire_time` 为准 |

## 验收与交付证据

按实际实施范围检查，不把全部可选能力作为所有商家的强制门槛：

| 场景 | 验收点 |
| --- | --- |
| 单笔开票 | 原订单和支付信息正确；申请号已保存；查询成功且票面金额、抬头、税率符合商家输入 |
| 幂等和超时恢复 | 同请求号重试关联同申请；结果不明先查单；不同参数不会悄悄覆盖原申请 |
| 合并开票 | 多业务订单去重计算金额；集合和各支付快照完整；无重复计入总额 |
| 通知 | 商家实际接收并落库；重复消息不产生重复业务操作；查单可补偿缺失消息 |
| 下载 | 文件实际可读取；类型、大小和摘要与返回信息一致；文件未就绪/过期可恢复 |
| 红冲 | 原蓝票关联正确，规则满足；查询红票成功；分别核实退款与红冲结果 |

仅静态检查时报告“参数/工程验证完成”；执行过真实接口再报告实际状态。记录用脱敏订单标识和必要结果，避免存放凭据、完整个人身份信息或带访问权限的下载地址。
