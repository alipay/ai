# 企业支付集成工作流

执行任务沿用[全局阶段记录](../../../normal/telemetry.md)和[会话授权](../../../normal/conversation-telemetry.md)，产品标识为 `token-b2b`。有工程实现证据才记 `token.integration_implemented`；在本能力允许的环境完成验证并保有结果证据才记 `token.validation_completed`，注明是本地模拟还是产品非生产环境。只问问题时不建业务 run；仅使用服务仍记录执行阶段，不采集 query 或其摘要。

办理条件见[企业支付商家开通](../../../onboarding/token-pay/b2b.md)。本 Skill 不在生产执行创单、打款或退款。工程联调用所属产品的已授权非生产环境；没有相应环境时采用模拟回执和本地测试。只有现有测试材料不能报告已开通、真实到账或对账完成。

## 一、确定接入画像

先按 [protocol-selection.md](protocol-selection.md) 定位实际调用服务并识别技术栈。检查构建清单、源码、已有 HTTP/支付客户端、容器入口和 CI 命令，记录目标服务路径、语言依据、真实构建命令和测试命令。多语言仓库无法唯一定位时先询问用户，不按顶层文件或前端语言猜测。

技术画像必须包含：

| 字段 | 当前选择规则 |
| --- | --- |
| `language` | 实际调用服务的小写语言名，例如 `java`、`go` |
| `client_mode` | 有覆盖当前接口的官方 SDK 用 `OFFICIAL_SDK`，否则用 `DIRECT_GATEWAY` |
| `protocol` | 当前固定 `CLASSIC_GATEWAY_V2` |
| `security_mode` | 按开放平台配置选择 `PUBLIC_KEY` 或 `CERTIFICATE` |

再从业务选择推导接口范围，不让商户适配无关能力。

| 选择 | 必接能力 |
| --- | --- |
| 聚合收银 | 创单、跳转 `cashier_url`、查单、OpenMQ |
| 支付宝 PC / App | 聚合创单、目标终端产品准备、页面拉起、订单终态 |
| 银行转账 | 专属账户或聚合收银、账户查询恢复；按需接资金确认 |
| 企业网银 | 聚合收银、真实安全参数；按需提前咨询付款机构 |
| 指定渠道兼容 | 仅明确点名时读取 `bank-transfer-direct.md`，不作为默认方案 |
| 主动关单 | 关单、结果未知后的查单补偿 |
| 整单退款 | 退款、退款查询、全额退款关单通知处理 |
| 部分退款 | 退款、稳定 `out_request_no`、退款查询 |
| 退款资金明细 | 退款/退款查询的 `query_options` 及明细模型 |
| 独立管理银行账户 | 账户创建、主体修改、账户查询、`customer_id` 持久化 |
| 通过江苏银行开户 | 开户前向支付宝对接同学安全交接银行商户号、银行母户账号、账户名和银行联行号 |
| 资金对账 | 账单下载、文件安全、幂等解析、差异处理和审计留痕 |
| 银行待认款资金 | `fund.changed`、CONFIRM/REJECT、资金幂等与订单终态衔接 |

产品前置条件：

- 全部企业支付 OpenAPI 需要聚合收银 SAAS 产品 `I1210300001000016445`。
- 银行账户、资金确认和企业网银分别核对当前商户应用的产品与接口权限；不从聚合收银签约推断条件能力已开通。
- 使用调用企业支付接口的同一应用订阅 `alipay.trade.saas.order.changed`；选择 `BANK_FUND_CONFIRMATION` 时还必须订阅 `alipay.trade.saas.fund.changed`。消息分流、幂等和恢复见[企业支付 OpenMQ 通知](openmq-notification.md)。

只把产品和平台操作记入待办，除非存在平台回执或配置截图等证据，不把它们标记为已完成。

## 二、完成平台与应用准备

本 Skill 只实施商户自研接入。开始编码前逐项确认：

1. 企业支付产品为邀请制，产品已经签约并绑定到本次调用的商户自有应用。
2. 应用类型、`app_id`、商户 PID、产品合约、密钥或证书和授权关系属于同一商户、同一应用、同一环境。
3. 小程序、移动应用或网页应用均可承载自研接入；网页和移动应用在生产调用前已按平台要求完成上线。
4. 应用网关已配置为公网可访问的 HTTP/HTTPS 地址。按商户安全要求启用服务器 IP 白名单和 `biz_content` 加密；涉及平台要求证书模式的资金能力时使用证书模式。具体核对步骤见 [open-platform-setup.md](open-platform-setup.md)。
5. 研发、测试、预发和生产的网关、PID、`app_id`、密钥、产品合约、授权和业务订单号完全隔离，不能交叉复用。
6. 不引入服务商代调用身份，不接收或传递 `app_auth_token`。
7. 通过江苏银行开户时，按 [open-platform-setup.md](open-platform-setup.md) 完成四项开户资料的受控交接；资料原文不进入代码、日志或验收 manifest。

## 三、建立安全的 OpenAPI 客户端

根据已选支付方式和账户能力，按[企业支付集成契约](integration-contracts.md)确定订单、身份、支付确认及退款的实现范围。

1. `OFFICIAL_SDK` 使用目标语言的支付宝官方 SDK，不手写签名、验签、HTTP 参数排序或网关协议。记录官方来源、版本和当前企业支付方法的覆盖依据。
2. `DIRECT_GATEWAY` 完整遵循 [non-sdk-openapi-integration.md](non-sdk-openapi-integration.md)。Go 直连按[Go 经典网关实现指南](code-example-go.md)复用协议组件及其测试，其他语言按相同组件契约建立独立适配器和原生测试。
3. 把网关地址、`app_id`、支付宝公钥或证书、商户私钥引用、字符集和签名算法放入既有配置体系。私钥只从密钥服务或受控环境变量读取。
4. 固定经典 `gateway.do`、`sign_type=RSA2` 和 UTF-8。业务字段放在 `biz_content` 中，字段名使用 snake_case；不能混入 V3 REST 请求头签名。
5. 依据[接口契约](api-contract.md)封装所选业务画像涉及的方法，统一处理超时、网关错误、业务 `sub_code`、响应验签和平台 trace；只为接入画像选中的条件能力开放业务入口。
6. 先完成响应验签，再反序列化或使用业务字段更新订单。`DIRECT_GATEWAY` 必须验原始 `<method>_response` 或 `error_response` JSON 片段，不能重组 JSON。
7. 对请求和响应日志做字段级脱敏；不记录私钥、签名原文、完整 `biz_content`、原始响应、收银台凭证或访问令牌。
8. 每个运行环境复用一个正确初始化的客户端，不为每次请求重复加载密钥或创建连接资源。

适配层只负责协议。幂等策略、订单状态机、重试决策和履约应放在商户业务层。

## 四、设计商户本地订单事实

至少持久化以下事实，具体表名和模型服从商户现有设计：

| 事实 | 用途 |
| --- | --- |
| `out_trade_no` | 商户创单幂等键和主要关联键 |
| 首次创单业务快照或摘要 | 防止同号不同参数重试 |
| `order_no` | SaaS 订单定位和 OpenMQ 幂等 |
| `trade_no` | 渠道交易定位，可能在支付后才形成 |
| 本地订单状态与状态版本 | 防止消息、查询和前端回调并发覆盖 |
| `total_amount` | 核验通知和查询金额 |
| `cashier_url` 或跳转状态 | 将用户引导至支付宝收银台；注意脱敏和有效期 |
| `out_request_no` 与退款快照 | 部分退款幂等和退款查询 |
| 退款状态、最后查询时间和查询重试状态 | 区分渠道已受理、退款成功和受理结果未知，驱动退款查询补偿 |
| 已消费的 `order_no + trade_status` | OpenMQ 去重 |
| 最后查询/通知时间和平台 trace | 补偿、审计和排障 |
| 账单类型、账单日、下载状态和文件指纹 | T+1 下载幂等、文件审计和重复任务去重 |
| 对账批次和差异状态 | 区分待核验、已确认、已修复和人工处理 |
| `fund_no`、资金状态与状态版本 | 唯一关联待认款入金，防止重复或乱序消息回退状态 |
| `claim_request_no` 与请求快照 | 保证 CONFIRM 同号同参恢复 |
| `refund_fund_no` | 关联 REJECT 后的退款处理和 `REFUNDED` 终态 |

不要从 `order_no` 或 `trade_no` 解析业务含义。状态更新采用条件更新或事务锁，禁止终态被旧消息回退。

## 五、串联支付主流程

```text
商户后端生成并持久化 out_trade_no
  -> alipay.trade.saas.order.create
  -> 验签并保存响应
  -> 将 cashier_url 原样交给所选终端
  -> 付款方在聚合收银台选择可用支付方式
  -> 等待 OpenMQ，同时按超时策略主动 query
  -> 在本地事务中确认终态并触发一次履约
```

### 5.1 创单

1. 先在本地生成 `out_trade_no`，保存业务参数和金额，再调用创单。
2. 网络超时或 `SYSTEM_ERROR` 时不能换号。先用 `out_trade_no` 查询；无法确认时用完全相同的请求重试。
3. 相同 `out_trade_no` 的金额、标题、渠道、买家信息或其他业务参数变化会产生 `IDEMPOTENT_CONFLICT`。
4. `time_expire` 优先于 `timeout_express`；两者都不传时按平台默认有效期处理。

### 5.2 聚合收银与支付宝

1. 将响应的 `cashier_url` 当作不透明完整 URL，直接 302 跳转或下发给可信前端导航。
2. 不解析短链，不拼接查询参数，不缓存为永久链接，不调用收银台页面内部 HTTP 接口。
3. `redirect_url` 只用于用户支付后的页面导航。跳回商户页面时展示“处理中”也比直接发货安全。
4. 支付宝 PC 接入核对电脑网站支付，App 接入核对 App 支付；所选终端分别完成非生产页面拉起验证。
5. 默认不限制渠道；明确只接受支付宝时才传 `pay_channels=ALIPAY`。仍以 `TRADE_SUCCESS + pay_channel=ALIPAY` 确认履约。

### 5.3 银行转账

按[渠道接入](payment-channels.md)先完成账户基线，再提供专属收款账户或聚合收银台。账户创建使用稳定外部商户号，查询用于恢复和展示前核验。银行账号与户名只向已授权用户展示，不写普通日志。

选择 `BANK_FUND_CONFIRMATION` 时，付款先到账后按[资金认款与拒绝](bank-fund-confirmation.md)处理：`WAIT_CLAIM` 只建立资金事实；CONFIRM 同步返回并核验通过的订单 `TRADE_SUCCESS` 可进入订单状态服务，返回 `WAIT_BUYER_PAY` 时继续等待通知或主动查单；REJECT 后等待资金 `REFUNDED`。资金状态机与订单状态机必须分开。

### 5.4 企业网银

1. 核对当前应用的企业网银能力；基础验收至少覆盖 PC，App 按实际银行支持补充。
2. 默认由付款方在聚合收银台咨询并选择机构，不在创单时传机构参数。
3. 使用真实、已授权并与买方主体一致的 `security_params`。商户需要提前提示机构可用性时，才调用 `alipay.trade.saas.ebank.consult`。
4. 银行受理、付款回单和页面回跳均不履约；只有订单 `TRADE_SUCCESS` 且实际 `pay_channel=E_BANK` 才能履约。

### 5.5 终态确认与履约

1. 同时实现 OpenMQ 消费和主动查单；选择资金认款时，`fund.confirm` 同步订单结果也进入同一订单状态服务。
2. 核验通过的 `TRADE_SUCCESS` 才允许支付成功履约。`WAIT_BUYER_PAY` 继续等待，`TRADE_CLOSED` 停止支付。
3. 核对 `out_trade_no`、`order_no`、金额和应用归属后，在同一事务内更新状态、记录幂等事实并写履约事件。
4. 履约本身也必须幂等，不能只依赖消息去重。

## 六、串联关单与退款

### 6.1 关单

1. 关闭本地待支付订单前先做并发保护，避免关单与支付成功同时履约。
2. 优先使用已持久化的订单定位字段。
3. `CHANNEL_CLOSE_PROCESS_UNKNOWN` 或网络异常时先查单。查到 `TRADE_CLOSED` 视为成功，查到 `TRADE_SUCCESS` 转入已支付处理，仍待支付才使用原参数重试。
4. `TRADE_ALREADY_PAID` 不是可重试关单错误；需要退回资金时进入退款流程。

### 6.2 退款

1. 退款前确认本地支付成功、剩余可退金额和并发资金操作。
2. 部分退款必须先生成并持久化唯一 `out_request_no`；整单退款可以不传。
3. 相同 `out_request_no` 只能重放相同金额和原因。业务参数改变时生成新请求号。
4. 退款接口成功返回 `refund_status=REFUND_PROCESSING`、`fund_change=N` 时，记录渠道已受理和本地处理中状态，立即或按退避策略调用退款查询；不得标记退款成功、失败，也不得换号重新发起退款。
5. 退款接口成功返回 `refund_status=REFUND_SUCCESS`、`fund_change=Y` 时，才按同步退款成功终态处理。
6. `REFUND_PROCESS_UNKNOWN`、`SYSTEM_ERROR` 或网络异常表示无法确认是否受理，先调用退款查询，再根据查询事实决定是否使用原 `out_request_no` 和原参数重试。
7. 部分退款不发送交易状态 OpenMQ；商户必须通过退款查询确认。
8. 累计全额退款使主单关闭时会收到 `TRADE_CLOSED`，消费规则见 OpenMQ 参考。
9. 银行转账退款可能因合作银行账户余额不足而失败。补足余额后，按原退款幂等语义查询并重试，不能换号制造另一笔退款。

## 七、错误、状态补偿与资金对账

### 7.1 错误与状态补偿

| 类型 | 商户动作 |
| --- | --- |
| 参数错误、产品未签约、幂等冲突 | 不自动重试；修正配置或使用正确的原参数 |
| 明确渠道拒绝 | 根据 `sub_msg` 和当前状态处理，参数变化时使用新业务号 |
| 退款明确受理中 | 保存 `REFUND_PROCESSING`，主动调用退款查询直到终态；不标记失败，不创建新退款 |
| 系统异常、超时、结果未知 | 无法确认是否受理，先主动查询，再按查询事实决定是否以原幂等号和原参数有限重试 |
| OpenMQ 重复 | 命中消费幂等记录后直接成功确认 |
| OpenMQ 延迟或丢失 | 定时扫描长时间非终态订单并主动查单 |
| OpenMQ 乱序或与本地冲突 | 不回退终态，主动查单并以查询结果校准 |
| 认款已受理 | 保存资金与订单关联，等待订单通知并主动查单，不提前履约 |
| 认款结果未知 | 使用原 `claim_request_no` 和原参数恢复，不换号 |
| 拒绝退款处理中 | 保存 `refund_fund_no`，等待 `fund.changed=REFUNDED` |
| 响应验签失败 | 不更新业务状态，记录脱敏告警并人工排查 |

重试采用有上限的指数退避并加入随机抖动。不能无限快速重试，也不能为不确定结果更换幂等号。

这里的状态补偿是用交易查询或退款查询恢复单笔业务事实，在验收清单中称为 `status_reconciliation`，不等于资金账单对账。

### 7.2 账单下载与资金对账

选择 `BILL_DOWNLOAD` 后按以下流程实现：

```text
按北京时间账单日调度 T+1 任务
  -> alipay.trade.saas.billdownloadurl.query
  -> 验签并取得短期 download_url
  -> 商户后端立即下载并校验文件可读性
  -> 保存受控原始文件、文件指纹和批次事实
  -> 按 bill_type 对应格式幂等解析
  -> 与商户订单、支付和退款事实逐笔核对
  -> 生成差异，不直接覆盖本地终态
  -> 对状态差异调用交易/退款查询复核
  -> 自动修复可确认差异，其余进入人工处理
```

实施约束：

1. `bill_date` 必须早于北京时间当天。`BILL_FILE_NOT_READY` 使用相同 `bill_type + bill_date` 退避重试，不把“未就绪”标记成当日无账单。
2. `download_url` 不落普通日志，不下发浏览器长期保存。后端下载成功后再推进批次状态；地址过期时重新查询，不复用旧地址。
3. 不假设四种 `bill_type` 文件列完全相同，为每种文件格式设置显式解析器、版本和必填列校验。
4. 对账至少识别商户单边、账单单边、金额不一致和状态不一致。金额使用精确十进制，禁止浮点比较。
5. 账单文件是核对事实，不直接驱动发货、关单或退款。状态冲突先调用对应查询接口确认，再进入统一订单状态服务。
6. 以商户、`bill_type`、`bill_date` 和文件指纹保证重复调度、重复下载、重复解析不产生重复差异或重复账务动作。
7. 原始文件、解析结果、差异处置和操作人按商户审计与留存策略受控保存；下载地址和敏感银行信息不作为审计正文。

## 八、测试矩阵

按[企业支付验收清单](completeness-checklist.md)选择适用项，将构建、定向测试、非生产端到端记录与平台回执登记到工程的 manifest，再运行清单中的本地验收命令。

最低测试范围：

| 场景 | 必须断言 |
| --- | --- |
| 正常创单 | 请求签名、响应验签、`out_trade_no` 落库、收银台 URL 原样传递 |
| 非 SDK 规范化 | 排除 `sign` 和空值、保留 `sign_type`，中文、空格、`+`、`%`、`&` 和嵌套 JSON 使用原值签名 |
| 非 SDK 原始响应 | 字段顺序、空白和转义不被重组；篡改、缺失签名、重复 root 和错误公钥全部拒绝 |
| 非 SDK 传输 | 签名后再 URL Encode，超时、取消、非 2xx 和超大响应显式失败 |
| 证书模式 | 请求序列号齐全；响应按可信 `alipay_cert_sn` 选证书，未知序列号失败关闭 |
| 创单网络超时 | 先查后重试，重试请求号和业务参数不变 |
| 同号同参重试 | 不创建重复商户订单或重复履约 |
| 同号异参重试 | 识别 `IDEMPOTENT_CONFLICT`，不覆盖首次快照 |
| 支付成功消息重复 | 只更新和履约一次，重复消息成功确认 |
| 目标消息 API 路由 | 信封 `method` 精确等于 `alipay.trade.saas.order.changed` 后才解析业务内容 |
| 资金消息 API 路由 | `fund.changed` 只进入资金消费者，`order.changed` 只进入订单消费者 |
| 支付宝 PC/App | 所选终端页面可拉起；回跳不履约，`TRADE_SUCCESS + ALIPAY` 才履约 |
| 企业网银 | 真实安全参数、机构咨询空结果、页面拉起和 `TRADE_SUCCESS + E_BANK` 终态 |
| 银行专属账户 | 账户创建幂等、查询恢复、受控展示和聚合收银链路 |
| 非目标或缺失 `method` | 即使业务字段形状相同也不进入订单状态机，不更新订单或触发履约 |
| 消息先后乱序 | 终态不回退；冲突时发起主动查询 |
| redirect 回跳 | 不直接标记支付成功 |
| 关单结果未知 | 查单后再决定成功、已支付或重试 |
| 整单退款 | 处理可缺失的 `out_request_no`，查询可恢复结果 |
| 部分退款 | 请求号稳定，重复请求不重复退款 |
| 退款明确受理中 | 成功响应映射为本地处理中，断言 `refund_status=REFUND_PROCESSING`、`fund_change=N`，随后调用退款查询且不创建新退款 |
| 退款结果未知 | 先退款查询，再重试原请求 |
| 全额退款关单通知 | 不重复关闭或重复冲正，金额与订单一致 |
| 待认款资金重复/乱序 | `fund_no + fund_status` 幂等，不重复发起认款或回退终态 |
| CONFIRM / REJECT | 两种 CONFIRM 模式、原号恢复、并发互斥和 `REFUNDED` 终态均覆盖 |
| 验签失败 | 不更新状态，不泄露签名和密钥 |
| 非生产端到端 | 创单、支付确认、查单及所选关单/退款能力有脱敏记录 |
| 账单文件未就绪 | 相同账单类型和账单日退避重试，不生成空账单结论 |
| 账单重复下载解析 | 同一文件不生成重复批次、差异或账务动作 |
| 账单差异 | 单边、金额和状态差异可分类；状态差异先主动查询复核 |
| 下载地址安全 | 不记录完整 URL，过期后重新查询，未授权入口不能取得文件 |

选择银行转账时增加账户创建/复用、查询恢复、受控展示和聚合收银链路测试；选择资金确认时增加资金通知、名称核验、认款/拒绝并发和非生产端到端测试。账单相关用例只在选择 `BILL_DOWNLOAD` 时触发。

## 九、Agent 实施要求

- 先读代码再决定文件结构；复用商户已有 HTTP 客户端封装、Repository、事务和测试工具。
- 输出语言识别依据；无法唯一定位实际调用服务时先询问用户，不生成猜测语言的实现。
- 只实现接入画像选中的条件能力，但基础创单、查单、OpenMQ、补偿、验签和幂等不能省略。
- 不生成真实密钥，不把用户提供的密钥写进仓库，不执行生产支付或退款。
- 每完成一段能力就运行目标语言真实编译和测试命令并登记证据，不到最后才补清单。
- 平台配置无法由代码证明时列为商户操作项，并使用 `external` 证据记录真实配置回执。
