## 一、适用边界

本流程只适用于商户使用自有应用、自有 PID 和自有密钥直接调用企业支付 OpenAPI。开始配置前确认不存在服务商代调用、第三方应用授权或 `app_auth_token`；存在这些身份时停止套用本流程并单独确认授权模型。

开放平台页面名称和菜单位置可能调整。以当前控制台展示和应用可见能力为准，不根据旧截图猜测入口；字段或权限与本 Skill 的契约快照不一致时记录差异并先确认平台事实。

## 二、应用和产品准备

1. 在开放平台选择或创建归属于接入商户的自有应用，记录应用类型、`app_id`、归属 PID 和目标环境，不记录任何密钥正文。
2. 确认应用状态允许目标环境调用。网页应用、移动应用等需要上线后才能生产调用时，保留平台上线结果。
3. 签约聚合收银 SAAS 产品 `I1210300001000016445`，并确认产品绑定到本次发起调用的同一个 `app_id`。
4. 选择单一银行转账创单或银行账户能力时，同时签约银行转账付款直连版 `I1210300001000016591`，并确认绑定关系一致。
5. 分环境核对应用、PID、产品合约和接口权限。测试、预发和生产不得交叉复用订单号、密钥或网关配置。

接口返回 `MERCHANT_PRODUCT_NOT_SIGNED` 或 `PERMISSION_DENIED` 时，先核对产品、应用、PID 和权限绑定，不通过更换业务参数或反复重试绕过平台前置条件。

## 三、身份、安全和网关配置

1. 使用支付宝官方 SDK 和平台支持的 RSA2 密钥或证书模式，不手写签名、验签和网关参数排序。
2. 在开放平台完成应用公钥上传或证书配置，并在商户配置中心保存对应的支付宝公钥或证书引用。核对密钥对、`app_id` 和环境一一对应。
3. 商户私钥只保存在密钥服务或受控配置中。控制台截图、联调记录、代码仓库和验收 manifest 不得包含私钥、完整证书私密材料、令牌或签名原文。
4. 生产配置参考：经典网关为 `https://openapi.alipay.com/gateway.do`、字符集 UTF-8 和 `sign_type=RSA2`。不得把 V3 REST 的 path 或 `authorization` 请求头签名用于当前 `alipay.trade.saas.*` 方法。启用 IP 白名单、`biz_content` 加密或证书模式时，以当前产品和商户安全要求为准。
5. 需要应用网关时配置公网可访问的 HTTP/HTTPS 地址，验证网络、证书、超时和重试策略。页面同步跳转地址不能代替消息或查单入口。
6. 保存一份脱敏配置对照，至少能核对环境、`app_id`、PID、产品、密钥/证书版本、网关和启用时间。

## 四、江苏银行开户资料交接

商户通过江苏银行开户时，在开户配置或联调前向支付宝对接同学提供以下四项资料：

| 资料 | 要求 |
| --- | --- |
| 银行商户号 | 使用江苏银行分配给该商户的正式商户号 |
| 银行母户账号 | 使用本次开户关系对应的母户账号，按字符串处理并保留前导零 |
| 账户名 | 与江苏银行开户资料中的账户名称完全一致 |
| 银行联行号 | 使用开户行对应的正式银行联行号，按字符串处理并保留前导零 |

交接要求：

1. 从江苏银行开户回执、协议或银行确认记录核对四项资料，确认其属于同一商户、同一开户关系；缺失或不一致时停止开户联调，不猜测或拼接。
2. 通过公司批准的受控渠道发送给身份已确认的支付宝对接同学，不通过公共群聊、普通日志、代码仓库或无权限文档传递。
3. `enterprise-payment-integration.json` 只登记脱敏工单号、交接时间和接收方角色等证据引用，不写入银行商户号、母户账号、账户名或联行号原文。
4. 资料变更时重新核对四项的一致性，并通知支付宝对接同学更新；不能只替换其中一项后继续联调。
5. 这四项是平台外的开户对接资料，不属于当前 `alipay.trade.saas.account.create`、创单或其他企业支付 OpenAPI 请求字段。除非开放平台正式契约新增字段，不修改 SDK 模型或 `biz_content` 透传这些资料。

## 五、OpenMQ 配置

### 5.1 平台侧准备

1. 确认企业支付交易状态消息 API 已发布为 `alipay.trade.saas.order.changed`，消息字段和生产权限已生效。
2. 使用调用企业支付 OpenAPI 的同一个商户应用订阅该消息 API，核对订阅应用 `app_id`、目标环境和接收方式。
3. 配置并验证商户的 OpenMQ 接收端、消费组或平台要求的接收参数。保留订阅成功回执或脱敏截图；代码中的常量不能证明订阅已生效。
4. 平台侧测试投递必须使用非生产环境，不由 Agent 发起生产真实交易。

### 5.2 商户接收路由

OpenMQ 投递包含协议消息信封和业务内容。`method` 是信封中的消息 API 路由字段，不属于交易状态业务字段。商户必须执行以下顺序：

```text
接收 OpenMQ 消息信封
  -> 按接入方式验证来源、签名和基础协议字段
  -> 读取信封 method
  -> method == alipay.trade.saas.order.changed
       -> 解析该消息的业务内容
       -> 进入企业支付订单状态消费者
  -> method 为其他已支持消息 API
       -> 路由到对应消费者
  -> method 缺失、空白或不受支持
       -> 不更新企业支付订单，记录脱敏告警并按统一未知消息策略隔离
```

路由约束：

- 对 `method` 做非空校验和精确字符串匹配，不使用模糊匹配、前缀匹配或大小写归一化。
- 使用 SDK 时从 SDK 暴露的消息信封属性读取 `method`；使用 HTTP/JSON 接收时读取顶层协议字段。不要尝试从业务内容中读取或推导 `method`。
- 不得因为业务内容含有 `trade_status`、`order_no` 等相似字段，就把其他消息 API 交给企业支付消费者。
- 共享入口应先完成通用信封路由，再由具体消费者校验业务字段。未知或永久不支持的 `method` 不能靠无限失败重投解决。
- 日志至少记录脱敏后的 `method`、消息标识和平台 trace；不记录签名原文或完整敏感业务内容。

## 六、非生产联调

至少验证以下场景并保存脱敏记录：

1. 目标 `method=alipay.trade.saas.order.changed` 能进入企业支付消费者并完成一次正常状态处理。
2. 其他 `method` 即使携带形状相同的 `trade_status` 和 `order_no`，也不会更新企业支付订单或触发履约。
3. `method` 缺失或空白时进入未知消息处理，不进入业务反序列化和订单状态机。
4. 支付成功、普通关单和累计全额退款关单按通知契约处理；部分退款不等待 OpenMQ。
5. 重复、延迟、乱序和消费事务失败时满足幂等、查询校准和事务提交后确认要求。
6. OpenMQ 异常或消息缺失时，主动交易查询仍能恢复订单终态。

## 七、验收证据

平台操作使用 `external` 或非生产 `run` 证据，代码行为使用 `test` 或 `run` 证据。至少保留：

| 检查项 | 可接受证据 |
| --- | --- |
| 应用和产品绑定 | 应用归属、应用状态及产品签约绑定的脱敏平台回执 |
| 身份和安全配置 | 环境、`app_id`、PID、公钥/证书版本及网关的脱敏核对记录 |
| 江苏银行开户资料交接 | 可追踪的脱敏工单或受控交接记录；不得包含四项资料原文 |
| OpenMQ 订阅 | 同一应用订阅 `alipay.trade.saas.order.changed` 的平台回执 |
| `method` 路由 | 目标、非目标、缺失 `method` 三类自动化测试或非生产运行记录 |
| 端到端通知 | 非生产创单、状态通知、查单补偿及业务幂等的脱敏记录 |

证据只证明其明确记录的事项。订阅截图不能证明消费者正确按 `method` 路由，路由单元测试也不能证明开放平台订阅已实际生效。
