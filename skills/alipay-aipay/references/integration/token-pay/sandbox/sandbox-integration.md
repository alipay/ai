# 周期订阅沙箱接入与联调

适用：支付宝托管周期订阅 `SUBSCRIBE_DEDUCT` 的接口接入、模拟支付签约、测试时钟和上线切换。沙箱不扣真实资金，但操作会改变沙箱数据；不据此推断自动续购、单笔支付或企业支付 B2B 支持同一沙箱。下述网页流程核对于 2026-10-20，能力仍以商户权限、实际页面版本和接口结果为准。

## 入口与最短路径

商家要求“帮我接入”或继续工程联调时，先读[沙箱自动接入交付](sandbox-delivery.md)，由 AI 优先通过随包[沙箱 CLI](sandbox-cli.md)执行登记、模拟确认、查询和测试时钟；CLI 不支持的准备步骤使用下文页面，必要登录和授权确认再交接商家。本文的“填写、点击、导入”等描述是实际操作语义，不意味着全部必须手工完成；不得把页面步骤虚构成通用 OpenAPI。只想体验网页时可直接使用下文指南。

打开[订阅沙箱工作台](https://b.alipay.com/page/checkout-management/subscription-test/sandbox)

| 用户当前目标 | 从哪里开始 |
|---|---|
| 自研系统接入沙箱 | 完成下面的接口调用授权，使用商家工程的沙箱 OpenAPI 创建业务，再由 CLI 或工作台模拟确认 |
| 暂无接入代码，先体验一笔订阅 | 使用[沙箱小店](https://renderpre.alipay.com/p/yuyan/180020010001298792/index.html)创建测试订阅，再到工作台模拟支付；确认页面实际连接沙箱，本地预览或示例数据不能作为联调证据 |
| 已取得支付或签约链接 | 直接按“导入本次操作”操作，不要求重新授权或创建商品 |
| 首笔已跑通，测试续费或到期 | 按“测试时钟”推进当前订阅的业务时间 |
沙箱工作台按订阅维度推进测试时钟。正式应用的测试客户验证属于生产环境，不能代替沙箱验证。

实际执行使用独立沙箱或本地模拟，与是否持有正式密钥无关。商家只要核对生产工程时，可查[生产代码和请求示例](../quickstart.md)与已有脱敏证据；本 Skill 不为验证改走生产网关。

选择沙箱的新商户先完成三步：**接口调用授权 → 创建订阅拿到长链 → 模拟支付并查询权益**。不以生产产品开通、生产授权或经营准备阻止沙箱起步，正式申请可以同时继续；不因某次沙箱调用失败自动切到生产。

## 第一阶段：完成接口调用授权与配置

### 准备沙箱应用和通知

1. 按[公共沙箱配置](../../sandbox/sandbox-setup-guide.md)准备环境并执行 `runtime.mjs sandbox ensure "<项目绝对路径>"`，附会话参数。标准配置不存在时通过 CLI 获取完整配置；已有标准配置则复核复用。基础凭据不再以浏览器获取为默认步骤。
2. READY 后从项目根 `.alipay-sandbox.json` 的 `appIds[0]` 读取 APPID、两种私钥和公钥，商户 PID 取 `sandboxAccounts.partner.userId`。服务端按原 SDK/签名逻辑选择私钥字段；不复制到 YAML/.env，不改变应用身份。请求继续使用 RSA2、UTF-8。
3. SDK 网关使用 `https://openapi-sandbox.dl.alipaydev.com/gateway.do`。`openapi-sandbox` 使用连字符，不是 `openapi.sandbox`；应用、密钥和资源 ID 都必须属于同一沙箱环境。
4. 在沙箱应用的“应用网关地址”填写商家接收通知的公网 HTTPS 地址，不填“授权回调地址”。在“消息服务 → FROM 平台”选择 HTTP，订阅 `alipay.trade.subscription.changed`。
5. 商家端验签、去重并可靠保存处理结果后，返回 HTTP 200 和纯文本 `success`；用 `alipay.trade.subscription.query` 补查遗漏状态。消息语义见[通知指南](../notification-guide.md)。

服务端基础凭据只读取统一 JSON，网关使用上述沙箱常量。`notify_url`、`return_url` 和端口仍放在商家原有业务配置中；它们不是沙箱凭据获取字段。买家资料完整保存在 JSON，订阅模拟确认不因此增加买家密码输入。

真实密钥通过服务端安全配置注入，不放在网页、对话、示例包或日志中。OpenAPI 资源归属由签名应用与商户身份决定，页面识别出的 PID 不会替换调用方的 APPID 和密钥。

### 在工作台登记

向商家解释为“接口调用授权”：把沙箱商户和调用接口的应用登记到沙箱服务，不把它讲成服务商接入模式。

1. 打开工作台右上角的授权入口。
2. 填写“授权商户 PID”和“沙箱 APPID”，点击“确认授权”。
3. 看到“沙箱调用配置已登记”或“该商户和应用已登记”后继续接口测试；同一组合已经登记时可跳过。

日常联调只需粘贴链接，工作台自动识别所属商户，无需再填 PID 或点击旧版“使用此商户”。网页不收集私钥，登记不会修改开放平台应用公钥；已有应用应核对密钥匹配，不自行覆盖公钥。`AUTH_KEYS_NOT_CONFIGURED` 表示沙箱服务缺少配置，交对接人员处理，不反复换 PID 或在网页填私钥。

完成标志：应用登记成功、服务端配置就绪、通知入口已准备。登记成功不等于接口或密钥已验证，也不能代替正式产品开通和正式应用授权。

## 第二阶段：创建首笔订阅并完成模拟支付

默认例子：每月 19 元、立即生效、单订阅项、无试用优惠。业务参数放在 `biz_content`；完整字段与互斥关系见[API 参考](../api-complete.md)，不把工作台操作当成新增商家通用 OpenAPI。

| 顺序 | 接口 | 输入与返回值 |
|---|---|---|
| 1. 创建商品 | `alipay.trade.product.create` | 名称可用“云盘-高级会员-月度订阅”，保存 `product_id`；命名规则见[商品指南](../api-product.md) |
| 2. 创建循环价格 | `alipay.trade.price.create` | 关联商品，`unit_amount=1900`，`recurring.interval=MONTH`，`recurring.interval_count=1`，保存 `price_id` |
| 3. 创建客户 | `alipay.trade.customer.create` | 为商家测试用户创建客户并保存 `customer_id`，它不是支付宝用户 ID |
| 4. 创建订阅 | `alipay.trade.subscription.create` | 传入客户和价格，保存 `subscription_id` 及本次返回的 `alipay_jump_schema` 完整长链 |

已有同一沙箱应用与商户下的商品、价格和客户可以复用。创建订阅的最小业务参数如下；默认首笔与后续价格相同，可省略 `pay_amount`：

```json
{
  "customer_id": "YOUR_SANDBOX_CUSTOMER_ID",
  "items": [{ "price_id": "YOUR_SANDBOX_PRICE_ID" }]
}
```

仅席位商品另传正整数 `items[].quantity`，个体订阅不传。金额单位为分，19 元传 `1900`；链接中展示的元金额不直接当作接口金额。创建响应成功只代表可以继续支付，不应立即开通付费权益。

### 导入本次操作

1. 把本次 `alipay_jump_schema` 完整长链或包含该字段的完整返回 JSON 粘贴到工作台“粘贴接口返回结果”。
2. 点击“识别并打开收银台”，让工作台识别订阅、所属商户并查询当前操作；不要求手工选 PID。
3. 核对商品、金额、周期、操作和协议，点击“付款并开通”。协议默认勾选仍需主动确认，不会自动付款；仅签约则使用页面对应的签约确认动作。
4. 看到“模拟已完成”后查询订阅，并点击“刷新详情”核对。结果不明时先“刷新订阅状态”，不立即重复付款或重新创建。

`alipay_schema` 短链不能替代此入口要求的长链。解析只帮助定位，不验签、不自动付款，事实以查询为准；保留接口原始链接，不重写成工作台地址，也不把不支持的链接转到生产支付。仅有短链时回查本次完整响应中的长链，仍缺失则联系对接人员确认。

升级、降级、增减席位或恢复续订后，点击“＋ 导入新的操作”，使用本次新返回的支付或签约链接，不能复用旧首付单。**仅签约可以没有支付单**；显示 0 元表示本次不用付款，不代表以后免费，不为导入工作台新建支付单。

### 查询与权益验收

调用 `alipay.trade.subscription.query`。普通立即生效、无试用的订阅支付完成后应为 `ACTIVE`，并核对本次支付结果、当前/待生效订阅项、周期和商家会员权益；试用等场景按对应契约判断状态。

核对商家接收端同一订阅的通知验签、幂等、落库和权益结果。工作台“发送消息”用于查看记录；“已记录发送”或标注 mock、“未实际投递”的记录不证明商家已收到。`code=10000`、页面跳转和工作台回执也不能单独证明权益处理完成。

沙箱小店主要通过主动查询刷新权益，体验小店不能代替自研系统通知闭环验收。

### 首笔之后按需测试

上述四个创建接口、订阅查询，加上 `alipay.trade.product.query`、`alipay.trade.price.query`、`alipay.trade.subscription.modify` 共 8 个常用接口，需使用自己的沙箱 APPID 联调确认权限。变更值及核对重点：

| `modify_type` | 工作台与查询核对重点 |
|---|---|
| `UPGRADE` / `INCREASE_QUANTITY` | 完成本次支付或签约，核对补款、目标权益/数量以及周期保留或重置 |
| `DOWNGRADE` / `DECREASE_QUANTITY` | 完成返回链接要求的签约，保留当前权益，推进到约定时间检查目标套餐/数量 |
| `CANCEL` | 按 `cancel_at_period_end` 区分立即取消和期末取消预约，不把预约成功当作权益已终止 |
| `REVERT_CANCEL` | 仅撤销尚未实际生效的期末取消，导入本次签约长链并重新签约，再查询取消预约是否撤销 |

`REVERT_CANCEL` 保持原订阅 ID，同步受理不等于恢复生效，应收到 `item_cancel_revert` 通知或查询确认；已 `CANCELED` 不能通过它恢复。当前仅签约操作没有支付单是正常情况。重复调用后若导入报 `AMBIGUOUS_OPERATION`，先查询现有操作并确认服务版本，不反复调用修改接口或新建订阅来绕过。

试用、零元、席位、宽限期和 `UPDATE_GRACE_PERIOD` 按实际准入测试，试用期不支持独立增减席位。商品修改、预计退款查询、支付明细、独立退款及优惠券需另行确认沙箱开放范围；本指南不承诺工作台提供退款模拟按钮。用户需要退款时查[接口契约](../api-complete.md)和[通知指南](../notification-guide.md)，按实际开放范围验证终态，不把受理或取消成功当成退款成功。

## 第三阶段：测试时钟与生命周期

首笔生效后，在“概览与周期 → 测试时钟”点击“启用测试时钟”，输入推进天数后点“推进时间”，或拖动时间轴的“现在”标记选择未来时间；在确认窗口核对当前订阅和目标时间，点击“确认模拟”，处理结束后刷新时钟与详情。

时钟只影响当前订阅，同客户其他订阅和新建订阅不继承。启用后业务时间停在指定时刻，不随现实时间流逝；只能向未来推进，不能倒退。建议按天推进观察逐日行为，从头重测时新建测试订阅。

| 验证场景 | 操作与结果 |
|---|---|
| 续费成功 | 推进到规则允许续费的时间；出现“续费待支付”后点“查看续费支付单”，核对金额并“模拟支付成功”，再查新周期和商家权益 |
| 续费未付款、宽限期 | 保留续费单待支付并继续推进，观察提醒、到期及已配置宽限期的后续状态；`PAST_DUE` 不等于已经取消 |
| 期末取消 | 商家先发起期末取消并查询预约，推进到期末，核对取消生效且不再续费 |
| 下周期降级或减少席位 | 商家先发起变更并完成所需签约，推进到约定时间，核对目标权益和下期金额 |
| 恢复续订 | 先完成 `REVERT_CANCEL` 返回链接要求的签约并查明取消预约已撤销，再推进验证续费 |

续费由测试时钟触发，无需另找“触发续费”按钮，时钟也不绕过续费时间限制。沙箱手工确认模拟扣款结果；生产托管续费由支付宝按协议自动扣款，不要求用户每期主动付款。保留待支付只验证未付款生命周期，不能当作“余额不足”等支付渠道错误码注入。

推进中先等待或“刷新时钟”，出现“继续推进”/“恢复推进”时核对后继续同一次处理。超时、连接中断、结果不明时先查时钟、订阅与操作单，不盲目重复提交。续费单待支付可继续推进，首次购买或升级等其他未完成操作按页面提示处理；查询刷新不自动推进或付款。

期末取消预约本身不应禁止推进。若输入框置灰，先检查是否启用、是否正在推进或存在待核对结果，再刷新时钟；旧版页面可能因收银台操作查询异常锁住时钟，仍无法操作时请对接人员确认修复版本。不能把本地修复或代码推送当作网页已部署，也不要为解锁时钟反复取消或签约。

## 第四阶段：正式上线前独立核对

沙箱通过只能支持沙箱验证结论。下表供商家在其正式上线流程中另行完成；本 Skill 只核对配置和已有证据，不执行表中的生产操作：

| 项目 | 正式环境核对动作 |
|---|---|
| 产品与应用 | 按[开通指南](../../../onboarding/token-pay/guidance.md)完成产品签约、正式应用上线、必要支付能力和正式应用接口调用授权 |
| 网关、凭据与资源 | 按[生产配置](../production-environment.md)切换 `https://openapi.alipay.com/gateway.do` 和配套凭据，重新建立商品、价格、客户；不复用沙箱资源 ID、协议或交易 |
| 金额、周期与准入 | 按[商户默认管控规则](../merchant-default-controls.md)核对价格/整单金额、周期、普通首笔限制、试用准入、宽限期和累计新签额度；以当前正式资料及商户实际准入为准 |
| 通知与权益 | 在正式应用重新配置通知地址和消息订阅，验证验签、幂等、查询补偿及商家权益；付款、续费、失败、取消及按需退款由商家按正式流程验收 |
| 用户告知与上线准备 | 展示首期价格、试用期限、续费金额、周期和取消方式，再按[上线准备度](../../../onboarding/token-pay/guidance.md)核对正式证据 |

“沙箱测试代扣额度不限额”仅指沙箱该项额度，不代表其他金额、周期、权限和状态校验关闭，也不证明生产额度或风控放行。普通首笔的金额限制不直接套用升级/扩容补款。

分别报告沙箱接口调用、工作台模拟确认、商家通知闭环、生产真实交易的验证情况；不能用模拟结果证明真实扣款、结算、生产通知送达或已经可以上线。

## 常见问题

| 现象 | 优先检查 |
|---|---|
| HTML、404、`invalid-method` | 连字符域名、`gateway.do` 路径、方法名及沙箱开放范围；不改走生产或关闭验签 |
| `isv.invalid-app-id` | 沙箱 APPID、配套网关及应用状态；进入参数校验不证明业务成功 |
| 签名/验签失败 | 同一沙箱应用的密钥、公钥、RSA2 和原始响应；授权登记成功不证明密钥匹配 |
| `AUTH_KEYS_NOT_CONFIGURED` | 沙箱服务配置缺失，联系对接人员，不在网页填私钥或换 PID 重试 |
| 归属冲突、订阅不存在 | 沙箱 PID、签名 APPID 与资源归属；不能靠切换 PID 转移订阅 |
| 导入失败或仍显示旧首付 | 使用本次完整长链/返回 JSON，通过“＋ 导入新的操作”导入；短链不替代长链，仅签约不要求支付单 |
| `AMBIGUOUS_OPERATION` | 查询本轮待签约操作并联系对接人员核对修复版本；不盲选历史操作，不重复发起恢复或创建支付单 |
| 时钟没变化或输入框置灰 | 确认已启用并手动推进，刷新时钟核对执行状态；期末取消预约本身不应阻止推进，旧版问题按版本排查 |
| 没收到通知 | 应用网关地址、FROM 平台订阅、网络可达、验签与接收端响应；发送记录只作线索 |
| 写请求超时或结果不明 | 先查询是否已创建/处理成功，再按对应接口幂等规则恢复，不因结果不明重复创建 |

排障提供页面地址、订阅 ID、方法名、发生时间、操作步骤、请求编号及脱敏错误；不收集私钥、令牌或完整签名长链。
