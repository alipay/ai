# 商家工程中的沙箱自动接入交付

仅用于周期订阅的工程实施或继续接入，且已选择沙箱。不用于普通问答、仅体验小店或生产交易。目标是商家完成一次必要的登录授权后，AI 持续完成工程改造与沙箱验收；这是执行目标。基础凭据由[公共沙箱模块](../../sandbox/sandbox-setup-guide.md)通过 alipay-cli 获取和保存；另附订阅沙箱测试控制 CLI。公网回调和必要的平台身份验证仍需实际工具支持。平台可能分别要求开放平台登录、沙箱调用登记或追加验证，不能将它们视为一次登录自动授予的权限。

## 1. 先检查工程和工具，再给最小方案

- 读取现有语言、框架、配置、用户、套餐、支付和权益代码，发现可复用实现。已有工程在原架构内改造；没有目标工程且工作区无法确定时，只询问工程位置。用户明确要新建 Demo 才创建新工程。
- 沿用已有业务定价和权益。缺失且影响实现时集中询问必要业务决策；单纯验证可明确采用独立测试套餐，例如每月 19 元，不修改真实商品定价。默认普通商户、托管扣款、立即生效、单订阅项、无试用优惠；具体契约读 [subscription-contracts.md](../subscription-contracts.md)。
- 简述将修改哪些模块：商家用户与客户映射、套餐与价格映射、订阅与支付操作持久化、购买入口、通知、查询补偿、权益处理以及测试。用户要求接入已授权范围内的可逆实施时，说明方案后直接执行，不再把方案确认作为固定关卡。
- 先发现宿主工具及其说明，逐项确认下表能力。测试控制动作优先使用随包[沙箱 CLI](sandbox-cli.md)：从实际 Skill 安装目录执行 help/doctor，再核对所需命令；其他动作优先有明确契约的连接器或 API，不足时使用宿主支持的浏览器工具操作正式沙箱页面。不能把文档链接、插件已安装或网页可打开当作工具能力已经可用。

| 所需能力 | 可用性检查与缺失处理 |
|---|---|
| 工程读写与运行 | 能否编辑目标工程、启动服务、执行构建和测试；仅聊天环境缺少这些能力时说明需切换有工程工具的宿主 |
| 沙箱基础配置 | 公共 `sandbox ensure` 能否复用或创建完整 `.alipay-sandbox.json`；新建走 CLI，无需先浏览器获取密钥 |
| 凭据安全配置 | 服务端只读取项目根统一 JSON，完整保存两种私钥和买家资料；原 SDK/签名逻辑沿用，不复制到 `.env` 或对话 |
| 沙箱授权与通知配置 | CLI authorize 可登记应用，但不配置应用网关地址或订阅消息；需另外确认这些页面/工具能力；必须验证结果，不能仅凭按钮点击成功 |
| 模拟支付与测试时钟 | 优先 CLI operation resolve/confirm 和 clock inspect/bind/advance/resume；核对本次操作和退出码，能力缺失时按 [sandbox-integration.md](sandbox-integration.md) 使用实际页面 |
| 商家运行与结果观察 | 能否启动服务，提供公网 HTTPS 通知入口，查询商家测试库或业务接口及脱敏日志 |

工具的名称、参数和权限以实际发现的工具契约为准。本表不是新 API 清单；不得编造账号申请、私钥导出、模拟支付或时钟接口，不直接调用从页面猜出的私有后台接口。

## 2. 最少人工交接与沙箱准备

1. 按当前已确认的订阅工程任务准备 CLI，调用公共 `runtime.mjs sandbox ensure "<项目绝对路径>"`（附本会话参数）。已有完整 JSON 直接复用；无配置的新项目通过 CLI 一次获得完整资料，不再先走浏览器获取应用和私钥。
2. 仅唯一 `FLOW:SANDBOX_CONFIG_READY` 后从对应文件取得应用、商户和密钥，供 SDK 与订阅 CLI authorize 使用。基础配置 READY 不代表调用登记、权限或通知已验证；待配置期间继续独立代码开发，不引用缺失字段。公共模块仅提供内部状态和本地配置，不调用 `sandbox summary`，不对客展示基础沙箱信息，也不接入收单的待配置或提醒消息；阻塞沿本产品流程记录和反馈。
3. 调用登记、通知配置等页面确需登录或追加验证时复用有效状态，只交接该动作所需身份验证。浏览器继续用于产品配置，不重复获取已有基础凭据；平台不支持当前应用配置时保留具体阻塞，不另建沙箱绕过。
4. 启动商家服务并检查接收端。优先复用商家已有测试 HTTPS 地址；使用隧道或测试部署时核对工具权限和任务范围，只暴露必要的测试入口，不公开数据库、管理端或凭据。需要额外付费或扩大访问范围时说明具体方案并取得授权。
5. 配置沙箱应用网关和消息订阅，验证连通性、签名与真实 API 权限。授权登记成功、HTTP 可达和业务调用成功分别留证。

用户请求完成沙箱接入时，合理范围内创建隔离测试资源、模拟付款、推进测试时钟均属于接入动作，无需逐次询问。操作前核对为沙箱且属于本次测试对象；不推进其他订阅、不切到生产、不执行真实扣款。页面提示、认证或工具权限仍须遵守。

## 3. 把代码接进商家业务

- 优先官方 SDK，按现有依赖和框架实现；相关示例是参考，不把其中 TODO 或注释当成已完成能力。
- 建立商家用户与 `customer_id` 的映射，保存商品、价格、订阅和本次操作标识；从商家购买接口发起订阅，沿用接口返回的完整支付长链。创建成功时不提前发放权益。
- 实现通知原始参数验签、幂等、可靠存储及权益更新；成功提交处理结果后才返回规定的 `success`。幂等键须按通知和业务事件契约选择，不能仅以订阅 ID 去重而丢掉后续续费。
- 实现主动查询补偿、超时后的结果核对以及取消生效处理。权益变动遵守 [notification-guide.md](../notification-guide.md) 和对应生命周期契约，不用前端跳转或沙箱工作台回执代替业务事实。
- 沙箱与生产用配置隔离，复用业务处理代码，不为测试增加绕过验签、直接修改会员状态或伪造支付成功的业务入口。测试桩仅用于明确标记的本地测试。
- 实际运行构建及相关测试，修复本次改动引起的失败。已有项目问题独立记录；构建失败不得宣称工程交付完成。

## 4. 自动运行最小验收

默认范围为下表全部项目；用户明确只做首笔时记录缩小范围，不宣称已完成续费和取消。使用独立测试用户和订阅，业务请求通过本次修改后的商家接口或服务执行；仅用独立脚本直调支付宝不能证明商家代码已接通。

| 场景 | 执行动作 | 通过证据 |
|---|---|---|
| 首次购买 | 建立或复用本任务商品、价格、客户；从商家入口创建订阅，导入本次长链并模拟付款签约 | 支付结果、订阅查询、商家通知处理及会员权益可关联到同一订阅；普通立即生效订阅为 `ACTIVE`，权益按套餐生效 |
| 通知可靠性 | 检查真实接收端；在隔离测试中验证重复通知、无效签名和查询补偿 | 真实沙箱通知已验签并处理；重复事件不重复发权益，无效签名不更新业务，补偿收敛到正确状态。分别标记真实投递与本地测试证据 |
| 一次续费 | 按网页规则启用并推进当前订阅时钟，定位续费支付单并模拟成功，等待或主动查询 | 同一订阅的新周期、续费支付结果和商家权益到期时间一致；后续事件未被首笔幂等记录吞掉 |
| 期末取消 | 发起期末取消并查询预约，推进到生效时间，再查询和检查权益 | 预约时当前权益保留；期末实际取消后按约定停止权益、不再续费；受理成功不当成已取消 |

商家权益若依赖本地定时任务，应使用现有测试时钟或可注入时间完成到期验证；沙箱时钟不会自动推进商家系统时间。不要调整主机全局时钟或伪造商家权益结果；缺少可控时间时标明该断言未验证。

以平台和商家两侧可关联的响应、通知、查询、持久化或业务接口结果判定。工作台仅有“已记录发送”、mock 或“未实际投递”时，通知闭环仍未通过；本地伪造通知、沙箱小店权益、测试桩或代码测试均不能替代真实沙箱投递。若平台当前无法实际投递，继续其他测试，并把通知列为阻塞，不给完整闭环成功结论。

## 5. 保存进度、恢复和停止条件

在商家工程本地保存简洁的接入记录（可沿用工程约定，默认 `.alipay-aipay-new/token-pay/sandbox-delivery.json` 并排除出版本控制；CLI 日志 `.alipay-aipay-new/token-pay/sandbox-cli/` 也须忽略）。每个外部变更或验收后更新，不把记录提交到公共仓库。字段建议：

- `environment` 固定为 `sandbox`，工程位置、Skill 版本、测试范围及方案假设。
- `identity` 保存应用与商户的本地引用或必要标识，`credentials_ref` 指向项目根 `.alipay-sandbox.json`，仅为安全配置位置，绝不保存私钥、令牌或授权码。
- `resources` 保存本任务商品、价格、客户、订阅及操作 ID，标明新建或复用；敏感支付长链只在受限运行数据中短期保存，不写进交付报告。
- `steps` 对每个动作记录 `NOT_RUN`、`RUNNING`、`PASSED`、`FAILED`、`BLOCKED` 之一，及时间、实际值、预期值、脱敏证据路径和失败原因；仅本地测试通过不能将真实沙箱步骤置为 `PASSED`。
- `pending_operation` 保存未决请求的接口、业务请求号和资源引用；`next_action` 记录继续位置；`cleanup` 记录本任务服务、隧道与测试资源的处置状态。

旧订阅 Skill 升级后续做同一任务时，从原商家工程目录查找 `.alipay-subscription/sandbox-delivery.json`（交付检查点）和 `.alipay-subscription/sandbox-cli/journal.jsonl`（CLI 操作日志）。从检查点的 `pending_operation` 与日志找到对应订阅、请求号及操作号。新旧记录都有时按同一业务请求核对，保留原证据。

例如上次测试时钟推进超时，从原工程运行下面的只读查询，将返回的操作号、目标时间和状态与原记录对照。只有确认是同一次推进且需要继续时，才按[CLI 恢复说明](cli/README.md#结果恢复和并发)处理。后续写操作显式带 `--journal ".alipay-subscription/sandbox-cli/journal.jsonl"` 可沿用旧日志；CLI 只向该文件追加记录，不会读日志自动去重或恢复。

```sh
node "<SKILL_DIR>/references/integration/token-pay/sandbox/cli/bin/sandbox.mjs" clock inspect --subscription-id "<原沙箱订阅ID>"
```

恢复时先核对工程版本、环境、应用归属与现有资源状态。历史检查点只是线索；代码、配置或外部状态变化后重验受影响步骤。已成功的创建操作不重复执行，复用资源须确认归属及用途一致。

外部写请求超时或结果未知时先查询，不直接重放；按各接口实际支持的幂等契约处理，不发明通用幂等参数。CLI 写请求退出码 4 先查原资源，退出码 5 按受阻原因处理。时钟推进中先查询进度或恢复同一次处理；`--wait` 只继续同一操作，`WAITING_PAYMENT` 时先确认对应支付单，再用已查询的 operationId/version 显式 resume；无法确认结果时保存未决状态并停止依赖它的写操作。确定失败后依据错误修复再尝试，重复出现同因失败且无新证据时停止盲重试。

确无工具、权限、平台能力或不可自动完成的身份验证时，只把该动作交给商家或标为阻塞，说明需要什么结果才能继续；其他可独立完成的工程与测试工作继续。不要为达到“一次授权”绕过平台追加验证，也不因工具缺失将全部后续工作改成商家清单。

## 6. 交付结论

交付可运行的代码、启动和测试命令、脱敏验收证据及恢复位置。说明本次改动、实际完成范围、人工介入点和仍缺的能力。

只有约定范围内的工程构建、真实沙箱调用、模拟支付签约、真实通知处理和商家权益断言全部通过，才能称“商家工程沙箱闭环已验证”；默认范围还须包含续费和期末取消。缺项时写“工程实现已完成，沙箱联调部分通过/被阻塞”，逐项报告，不能用模拟或离线测试替代缺失证据。

测试结束按约定关闭本任务临时服务与隧道，或为继续演示明确保留期限；保留所需证据和测试资源引用，不删除商家原有资源。沙箱交付不等于生产上线，不修改生产配置或发起生产交易。
