# 企业认证生命周期、通知与验收

方法及字段见 [api-contract.md](api-contract.md)，接入准备见 [integration.md](integration.md)。

## 两项独立状态机

| 能力 | 状态 | 含义 |
| --- | --- | --- |
| 企业认证 | `CREATED` | 待提交企业信息 |
| 企业认证 | `PROCESSING` | 认证处理中 |
| 打款认证 | `CREATED` | 待提交账户信息 |
| 打款认证 | `REMITTING` | 小额打款处理中 |
| 打款认证 | `WAITING_AMOUNT` | 等待用户输入实际到账金额 |
| 打款认证 | `VERIFYING` | 金额已受理、验证中 |
| 各自终态 | `SUCCESS` / `FAILED` | 各自认证成功/失败，不可被后续消息回退 |

创建链接、扫码、页面回跳、页面关闭或用户口述都不能代替可信结果。页面返回商家时由商家服务端查询最新结果；其他非终态按合理间隔查询并逐步退避，终态后停止轮询。不要将打款的 `WAITING_AMOUNT` 映射为认证失败。

## 幂等与恢复

- 同应用、同商户、同 `out_request_no` 的重复创建复用原订单，每次成功创建签发新链接。为两项认证分别保存认证域、请求号及平台订单号，不跨域查单。
- 创建超时或结果不明时先按原号查询；查到订单沿用它，确需重试创建时仍用原号，避免建立并行订单。
- 链接过期后同号重新创建以续签页面链接，不能从过期推定认证失败；已形成的结果仍可查询。
- 处理中继续查询，不新建第二笔认证强行重跑。`FAILED` 是终态，需要重新认证时使用新的请求号；新的一次独立认证也使用新号。
- 打款账号需要更换时创建新订单，不在原订单上替换账户。`REMITTING` 时等待到账流程，进入 `WAITING_AMOUNT` 后用户在托管页面输入金额。
- 金额填错可能回到 `WAITING_AMOUNT`，不代表整单已经失败，也不立即产生终态通知；次数耗尽或期限已到时以页面及渠道确认结果为准，不编造固定可尝试次数或到账时长，不建议猜金额、自动试金额或用新单绕过限次。
- 不解析或记录页面凭证，不把完整链接送入第三方统计。链接应仅交给本次认证的目标用户。

## OpenMQ 通知

企业认证：`alipay.trade.saas.enterprisecertify.changed`，主体 `enterprise_certify_detail_info`。

打款认证：`alipay.trade.saas.bankverify.changed`，主体 `bank_verify_detail_info`。

只在各订单首次进入 `SUCCESS/FAILED` 后触发终态通知，不通知每次页面操作或金额输入失败。企业消息业务字段与查询一致；打款消息与查询共用账户及终态字段，但**不包含 `match_expire_time`**。消息不是 HTTP `notify_url` 回调，不要套用订阅或发票消息主体。

通知发送到创建订单的调用应用，以 `APP_ID` 类型的应用 Tag 路由。商家应为该应用订阅对应消息 API；代调用场景尤其需要核对创建时调用应用，不能假设消息固定发给被代调用商户的其他应用。

使用平台支持的 OpenMQ 接收 SDK/协议完成消息验证、接收和应答，不凭业务主体猜测外层签名字段或 HTTP 成功应答。按 `certify_order_no:status` 或 `bank_verify_order_no:status` 幂等消费；落库成功后应答，重复投递不重复开通权益、触发认证或打款。终态不会被迟到的处理中信息覆盖，冲突时查单核对。

通知投递失败不会回滚认证结果。平台调用内对不确定的网络/系统异常可以同标识短重试，但不承诺无限补发或定时恢复。漏收、延迟或消费失败时，商家必须保留查询补偿，不能将“没收到消息”当作认证失败。

## 验收

按本次选择的认证能力验证，不要求所有商家先完成两项认证：

| 场景 | 应取得的证据 |
| --- | --- |
| 创建与页面 | 请求号与对应平台订单号已保存；目标用户可打开返回的完整链接；创建成功未误标为认证成功 |
| 同号重试与过期 | 同号仍关联同订单，新链接可恢复访问；不更改原业务结果或自动延长金额验证期限 |
| 企业认证 | 用户完成托管页面操作；查询到终态；正确使用法人证件尾号而非假设完整证件号 |
| 打款认证 | 小额到账及金额回填由目标用户完成；识别待输入、验证中和终态；不将填错金额直接标为整单失败 |
| 回跳 | HTTPS 导航返回后仍执行服务端查单，回跳本身不授予认证成功状态 |
| 通知与补偿 | 实际接收正确应用/消息主体的终态并落库；重复消费幂等；漏收时可通过查询核对 |
| 身份与数据 | 查询保持创建身份；不跨商户/应用访问；日志不输出完整链接、银行账号、证件信息及授权令牌 |

交付分别报告代码修改、静态验证、接口调用、用户完成认证以及商家收到通知的实际证据。未执行真实认证时明确说明，不把示例解析或单元测试成功当作业务认证通过。
