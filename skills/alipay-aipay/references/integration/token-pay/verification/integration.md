# 企业身份与对公账户认证接入

交付时按实际工程改动和验证结果说明接入进展，并注明验证是在本地模拟环境还是产品允许的非生产环境。

## 选择能力

| 用户目标 | 能力 | 用户完成的操作 |
| --- | --- | --- |
| 核验企业与法人身份 | 企业四要素核验与法人实名扫脸 | 在托管页面提交企业名称和统一社会信用代码，按页面指引完成法人身份核验和扫脸 |
| 核验对公账户 | 对公账户打款认证 | 在托管页面填写账户及开户行，等待小额到账，回填实际到账金额 |

两项服务可分别开通、分别完成、分别查询。打款认证不要求先完成企业四要素认证，后者也不依赖打款认证。不要构造统一认证主单或把一项成功映射为另一项成功。这里不提供独立个人实名认证通用接口，也不是 API 签名、应用授权或钱包授权服务。

资料入口：[开放平台认证资料一](https://opendocs.alipay.com/pre-open/0kgpl9?pathHash=e95969aa)、[开放平台认证资料二](https://opendocs.alipay.com/pre-open/0kgo2q?pathHash=35f894d2)。本组资料于 2026-11-03 按当前接入指南与接口实现核对；此次未取得这两个网页正文，不擅自判定两个链接各自对应哪项产品。权限、测试环境、收费及正式开放范围以当前控制台和业务接入资料为准，不虚构平台能力尚未上线或已完成本次商户验收。

## 商家准备

- 选择需要的认证产品，按实际产品准入流程申请权限及应用绑定。企业认证权限、对公账户打款认证权限和支付权限分别核对，不要求所有能力一并开通。
- 应用 AppId、商户身份、产品权限、密钥和环境保持一致。沿用工程已有支付宝服务端 SDK、RSA2 签名和响应验签配置；私钥只保存在服务端。
- 普通自研应用使用自身调用身份。第三方应用代商户调用时，须已有应用授权和代调用关系，并通过网关公共参数携带有效 `app_auth_token`；不放入 `biz_content`。不要套用企业支付的“仅自有应用”限制。
- 不要求用户在聊天中提供法人完整证件、扫脸素材、银行账号、到账金额或密钥。企业资料、法人核验、账户资料和金额回填由目标用户在支付宝托管页面完成。
- 创建接口不接受业务体中的商户 PID；订单身份由可信调用上下文确定。查询保持与创建相同的应用及商户身份，避免将代调用的商户与调用应用混为一谈。
- 如需回跳，准备商家控制的公网 HTTPS 页面；不要根据托管页面域名推导网关、测试地址或登录地址。

## 实施流程

1. 检查现有商家工程的企业客户模型、服务端支付宝调用、认证入口和消息接收能力。按用户指定的认证域推进，不把直接问答改成完整接入任务。
2. 为一次独立认证生成 `out_request_no`，调用对应创建接口；保存业务客户、请求号、认证域、应用身份及返回的平台订单号。
3. 将完整 `page_url` 直接跳转或生成二维码交给目标用户。链接是不透明凭证，不拆解、拼接、替换域名，不调用托管页面内部接口。
4. 用户在页面完成操作，商家服务端通过查询和 OpenMQ 获取结果。展示处理中、成功、失败；回跳仅做页面导航。
5. 处理同号重试、链接续签、终态通知幂等及查询补偿。接口字段见 [api-contract.md](api-contract.md)，恢复及验收见 [lifecycle.md](lifecycle.md)。

优先官方 SDK；SDK 尚无对应专用请求类时，使用该语言 SDK 已支持的通用调用能力并核对方法名、业务 JSON 和响应验签，不虚构 SDK 类名。不自建法人资料或到账金额采集流程来绕开托管页面。商家需要正常开发和查询时继续实施，用户本人完成身份确认、扫脸和实际金额回填。

## 与订阅、支付和发票的关系

企业客户购买服务时，商家可以按自身业务规则要求认证；认证成功不会自动创建订阅、签约扣款、完成付款或开票。认证用的小额打款不是 B2B 收款或用户订单付款。两个认证接口族虽然都以 `alipay.trade.saas.*` 开头，仍使用本目录契约，不读取 B2B 账户和退款流程替代认证流程。

不将订阅沙箱、测试客户或测试时钟推断为认证沙箱。已有明确授权的认证非生产环境时沿用；否则在工程内模拟托管链接、状态通知和查询结果。不要自行对生产客户发起认证或小额打款测试。

## 结果数据边界

企业认证查询返回企业名称、统一社会信用代码、法人姓名及证件尾号，不返回完整法人身份证号码或扫脸材料。打款认证查询返回完整对公账号、户名及开户行信息，不返回实际打款金额。商家应按必要用途控制访问、落库和展示，不记录完整页面链接、授权令牌或敏感认证结果到普通日志。
