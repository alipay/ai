# 商家测试推进后台指南

**生产专用 · 仅供商家了解已有平台操作或核对证据。** 下文推进、账号绑定、通知地址和示例均指符合准入的商家在生产平台的操作，不是授权 Agent 发起请求。本 Skill 不在生产创建/推进测试客户、不绑定账号、不触发续费、退款、打款或访问生产通知内容；没有已有证据时保持待核验。

本指南是生产环境测试客户的推进能力。周期订阅沙箱工作台使用独立沙箱应用与网关、模拟支付和订阅维度测试时钟，见[沙箱接入指南](sandbox/sandbox-integration.md)；不要把下文生产客户打标、账号绑定流程直接当作沙箱工作台的前置条件。

新商户使用生产应用和生产网关接入时，需要验证订阅全流程（续费、取消、降级生效、试用期结束等场景）。这些场景按正常时间自然发生时测试周期较长，会影响接入效率。

为加速生产环境验证流程，支付宝订阅产品提供**商家测试推进后台**，允许商户针对**测试客户**自主推进周期场景，无需等待自然到期。API 请求仍使用生产应用凭据和 `https://openapi.alipay.com/gateway.do`。

## 一、入口与适用范围

### 1.1 后台地址

- **订阅测试工作台**：[https://b.alipay.com/page/checkout-management/subscription-test/list](https://b.alipay.com/page/checkout-management/subscription-test/list)
- **测试客户管理**：[https://b.alipay.com/page/checkout-management/subscription-test/customers](https://b.alipay.com/page/checkout-management/subscription-test/customers)

> ⚠️ 工作台目前仅对已完成订阅产品开通的商户开放，访问时需先登录支付宝商家平台，且登录账号
> 需具备对应商户身份。如登录后仍无法访问，请联系支付宝订阅对接同学确认权限。

### 1.2 适用范围

| 维度 | 说明 |
|------|------|
| 适用阶段 | 商户接入联调、验收阶段，用于加速周期场景验证 |
| 适用对象 | **仅测试客户**的订阅 |
| 是否影响生产 | 仅对明确标记的测试客户生效，不改变正式客户的订阅与通知 |
| 是否需要开发 | **无需开发**，后台可视化操作 |

> ⚠️ **重要约束**：测试推进仅对测试客户生效。普通（非测试）客户的订阅不允许通过该后台触发，调用会被拒绝并提示“客户非测试客户”。普通客户仍按正常业务时间自动流转。

### 1.3 将客户标记为测试客户（打标）——使用前必做

测试推进只对**测试客户**（客户系统 `isTest=true`）生效，因此发起推进前须先把对应客户打上测试标。商家通常已经通过自己的接口（`alipay.trade.customer.create`）创建过客户、手里已有 `customer_id`，此时**无需重新创建**，直接对已存在的客户打标即可。

**打标步骤**：

1. 进入[测试客户管理](https://b.alipay.com/page/checkout-management/subscription-test/customers)
2. 选择 **“添加已有客户”**（不要选“新建客户”，避免重复创建）
3. 填入已通过 `alipay.trade.customer.create` 创建得到的 **`customer_id`**
4. 提交后该客户即被标记为测试客户（`isTest=true`），其订阅方可用于后续推进操作

> 💡 **常见误区**：
> - 商家已有自己的客户体系并已调接口创建过客户时，**应选“添加已有客户”并填 `customer_id`**，而非另建一个新客户——否则推进时用的是未打标的老客户，会被拒绝并提示“客户非测试客户”。
> - `customer_id` 须与创建订阅时使用的一致，建议直接从 `alipay.trade.customer.create` 的返回值或本地存储中取。
> - 打标后稍等片刻再发起推进；若仍提示“客户非测试客户”，确认填入的 `customer_id` 是否打标成功。

### 1.4 绑定测试用支付宝账号（续费推进前）

“模拟下周期续费”会校验测试客户绑定的支付宝账号与该订阅当前扣款账号是否一致。为避免推进时
被拒绝，创建或添加测试客户时应完成支付宝账号绑定，并使用该账号完成测试订阅的支付与签约。

**绑定步骤**：

1. 在“测试客户管理”的新建或添加页面，为目标测试客户选择“绑定支付宝账号”
2. 使用准备承担该测试订阅扣款的支付宝账号扫码并确认；二维码有效期为 **15 分钟**
3. 等待后台显示“已绑定”，并核对页面展示的脱敏手机号或脱敏支付宝账号
4. 保存测试客户后，使用同一个 `customer_id` 创建订阅，并由刚绑定的账号完成支付与签约

已存在的测试客户也可以重新进入管理页面补绑或换绑。重新绑定只替换该测试客户当前绑定的
支付宝账号，不会新增测试客户，也不会额外占用测试客户配额。一个测试客户同一时刻只保留一个
当前绑定账号；同一个支付宝账号可以用于多个测试客户。

> 绑定测试用支付宝账号不会改变 `customer_id` 的含义：`customer_id` 仍是客户ID，不是
> 支付宝用户ID。该绑定仅用于测试客户管理和测试推进校验，也不能替代用户在支付宝页面完成
> 实际支付与签约。

## 二、支持的操作类型

后台支持针对测试客户的订阅推进以下 4 类周期场景。

| 操作 | 可观察结果 | 典型验证场景 |
|------|-----------|------------|
| **模拟下周期续费** | 发起本周期扣款并推进至下一周期 | 验证续费扣款、续费成功通知 |
| **取消订阅** | 执行已预设的周期末取消 | 验证取消通知及订阅状态流转 |
| **降级生效** | 让待生效的降级进入下一周期 | 验证降级在下周期生效后的状态 |
| **试用期结束** | 结束试用期并进入正式订阅流程 | 验证试用期转正式的扣款与“生效中”通知 |

> 各操作在后台提交后，系统会按后续章节的前置条件执行。条件不满足时会直接返回失败，不改变当前订阅状态。

## 三、各操作前置校验

不同操作对订阅状态和待生效操作有不同要求。商户在后台发起操作前，建议先通过查询接口确认订阅当前状态，避免因条件不满足被拒绝。

### 3.1 模拟下周期续费

| 校验项 | 条件 | 不满足时的提示 |
|--------|------|----------------|
| 订阅状态 | 处于“生效中”或“试用中” | 订阅状态不允许此操作 |
| 操作可用性 | 当前订阅已进入可推进的续费阶段 | 当前操作暂不可用 |
| 待取消标记 | 未设置周期末取消 | 订阅状态不允许此操作 |
| 支付宝账号一致性 | 测试客户绑定的支付宝账号必须与该订阅当前扣款账号一致 | 测试客户未绑定支付宝账号，或绑定账号与当前扣款账号不一致 |

> 支付宝账号一致性校验只针对“模拟下周期续费”。取消、降级生效和试用期结束仍按各自的状态
> 与待生效操作条件校验。

### 3.2 取消订阅

| 校验项 | 条件 | 不满足时的提示 |
|--------|------|----------------|
| 订阅状态 | 处于“生效中” | 订阅状态不允许此操作 |
| 操作可用性 | 周期末取消已设置并可推进 | 当前操作暂不可用 |
| 待取消标记 | 已设置为周期末取消（即先预设到期自动关闭，再执行推进） | 订阅状态不允许此操作 |

### 3.3 降级生效

| 校验项 | 条件 | 不满足时的提示 |
|--------|------|----------------|
| 订阅状态 | 处于“生效中” | 订阅状态不允许此操作 |
| 操作可用性 | 降级变更已受理并可推进 | 当前操作暂不可用 |
| 待生效降级 | 存在“待生效”状态的降级订阅项 | 订阅状态不允许此操作 |

### 3.4 试用期结束

| 校验项 | 条件 | 不满足时的提示 |
|--------|------|----------------|
| 订阅状态 | 处于“试用中” | 订阅状态不允许此操作 |
| 操作可用性 | 当前试用订阅已进入可推进阶段 | 当前操作暂不可用 |

## 四、执行结果与异常

### 4.1 单次推进状态

| 状态 | 说明 |
|------|------|
| 执行成功 | 推进请求已成功受理或完成 |
| 执行失败 | 推进失败，后台会返回可用于排查的错误信息 |
| 已跳过 | 跳过执行 |

> 「模拟下周期续费」为异步扣款：若扣款单已发起（含重复推进时扣款单已处于扣款中），返回执行成功、提示"触发成功，等待异步扣款完成"，实际扣款结果以异步通知为准。

### 4.2 常见异常与排查

| 异常提示 | 说明 | 排查建议 |
|----------|------|---------|
| 参数校验失败 | 订阅 ID / 客户 ID / 操作类型缺失或无效 | 检查各项参数是否完整有效 |
| 客户非测试客户 | 当前客户不是测试客户 | 确认客户已标记为测试客户后再发起 |
| 测试客户未绑定支付宝账号 | 续费推进无法确认目标扣款账号 | 返回测试客户管理页面，扫码绑定后再重试 |
| 绑定账号与当前扣款账号不一致 | 测试客户绑定的账号不是该订阅当前扣款账号 | 核对创建订阅时实际完成支付与签约的账号，并将测试客户重新绑定到该账号 |
| 绑定二维码已失效或尚未完成 | 扫码绑定超时，或用户尚未确认 | 刷新二维码，在 15 分钟内使用目标支付宝账号完成扫码 |
| 订阅不存在 | 订阅 ID 对应的订阅未找到 | 检查订阅 ID 是否正确 |
| 订阅状态不允许此操作 | 订阅当前状态不满足该操作的前置条件 | 查询订阅当前状态，对照第三章前置校验调整 |
| 当前操作暂不可用 | 订阅尚未进入该场景的可推进阶段 | 稍后重试或检查订阅状态及待生效操作 |
| 客户信息查询失败 | 服务暂不可用 | 稍后重试 |
| 推进失败 | 推进过程中出错 | 查看后台返回的信息；无法自行解决时联系技术支持 |
| 并发执行冲突 | 同一订阅已有推进操作在执行 | 等待完成后再试 |

> 在订阅详情页可查看每次操作的执行回执，对照上表定位异常原因。

## 五、边界与约束

1. **测试客户限制**：仅测试客户可触发，非测试客户调用直接被拒绝并提示“客户非测试客户”。
2. **正式业务隔离**：测试推进不会改变正式客户的订阅，也不会把正式客户通知发送到测试地址。
3. **绑定账号限制**：支付宝账号绑定只用于测试客户；存量测试客户可以换绑，未绑定或绑定账号与当前扣款账号不一致时不能执行模拟下周期续费。
4. **异步结果确认**：续费、试用转正式等异步场景以最终通知和查询结果为准，后台显示“触发成功”不等于扣款成功。

## 六、推荐验证路径

建议商户在后台按以下顺序推进测试，逐个验证通知与状态流转：

1. **准备测试客户**：创建或添加已有客户，完成测试客户打标，并绑定准备承担测试扣款的支付宝账号
2. **创建测试订阅**：使用同一个 `customer_id` 创建订阅（个体 / 试用期 / 团体席位均可），由已绑定账号完成支付与签约
3. **续费验证**：订阅处于“生效中”或“试用中”时发起续费推进，预期收到续费成功通知（试用期为转为“生效中”的通知）
4. **降级生效验证**：先调用订阅变更接口发起降级，确认收到降级通知后，发起降级生效推进，验证下一周期生效后的状态
5. **取消验证**：先设置周期末取消，确认收到第一阶段 `change_type=cancel_at_period_end` 通知且订阅仍可用；再执行取消推进，确认收到最终 `change_type=cancel` 通知，查询订阅状态为 `CANCELED`
6. **试用期结束验证**：对“试用中”状态订阅执行试用期结束推进，验证扣款与转为“生效中”的通知

> 推进操作后，请以收到的异步通知为准更新本地订阅状态，通知处理规范见 [通知完整指南](notification-guide.md)。

## 七、与接口接入的关系

- 测试推进后台是**接入验证辅助工具**，不替代正式接口接入流程
- 商户上线后，普通客户仍按正常业务时间自动流转，**无需也不允许**通过该后台手动推进

## 八、订阅通知测试地址联调

### 8.1 背景

存量商户做迭代开发时，可为**测试客户**单独指定测试通知地址，以便隔离联调流量，**不影响正式客户与线上通知**。该能力仅对 `isTest=true` 的客户生效。

### 8.2 支持的通知类型

| 通知 | 含义 |
|------|------|
| 订阅变更通知 `alipay.trade.subscription.changed` | 订阅生效、续费、取消、试用期签约等变更 |
| 可扣款通知 `alipay.trade.subscription.pay.notify` | 非托管模式扣款窗口开始前预通知 |

### 8.3 使用步骤

1. **创建并打标测试客户**：在商家后台创建客户并标记为测试客户（`isTest=true`），打标方式见 1.3 节。正式客户（`isTest=false`）的通知始终走生产应用默认通知地址，不受影响。
2. **配置测试客户专用通知地址**：在商户配置中按测试客户 `customer_id` 配置通知地址，如 `https://your-test-server.example.com/notify`。地址须为可达的 HTTPS 地址；**未配置时该测试客户也按生产应用默认通知地址接收通知**。
3. **发起业务流程联调**：用该测试客户发起订阅、续费、取消、扣款等操作；配置有效时，相关通知会投递到测试地址并携带与正式通知一致的报文。

### 8.4 通知地址选择规则

| 客户与配置 | 通知地址 |
|-----------|---------|
| 测试客户，且已配置有效测试地址 | 仅投递到测试地址 |
| 测试客户，但未配置测试地址 | 投递到生产应用默认通知地址 |
| 正式客户 | 始终投递到生产应用默认通知地址 |

### 8.5 通知报文

通知报文内容与正式通知**完全一致**，测试服务端按现有正式通知的验签与解析逻辑处理即可，无需针对测试地址额外改造（验签/解析规范见 [通知完整指南](notification-guide.md)）。

### 8.6 常见问题

| 问题 | 答案 |
|------|------|
| 测试客户通知会同时发到线上地址吗？ | 不会。命中测试地址后，该条通知**只**投递到测试地址。 |
| 配了测试地址却没收到通知？ | 检查：① 客户是否已标记为测试客户；② 测试地址是否按该 `customer_id` 正确配置且非空；③ 测试服务端是否可达。 |
| 能把正式客户通知也转到测试地址吗？ | 不可以。本能力仅限测试客户，确保线上通知不受影响。 |
